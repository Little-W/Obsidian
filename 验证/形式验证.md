## 1. VC Formal

VC Formal 是一套面向 RTL 和网表的形式验证平台，核心思路是不靠随机仿真，而是把设计、约束和断言转成可求解的逻辑问题，从而在更大的状态空间里发现潜在缺陷。它特别适合在早期发现边界条件、协议违规、死锁、漏连、时序相关假设错误等问题。

## 1.1 适合应用的场景

- 协议检查：验证 AXI、APB、AHB、FIFO、握手通路等接口是否满足时序和行为约束。
- 断言验证：配合 SVA 对关键设计规则、状态跳转条件、异常处理路径做自动证明。
- CDC/RDC 相关问题：检查跨时钟域、跨复位域的信号是否存在亚稳态、握手缺失或复位释放风险。
- 等价性与回归确认：在优化、修复或重构后，确认前后逻辑行为一致。
- 安全关键设计：适合 CPU 控制逻辑、总线仲裁、状态机、权限控制、异常响应等需要高可信度的模块。
- 难以靠仿真覆盖的角落场景：比如极端输入组合、罕见状态迁移、不可达状态排查、深层死锁分析。

## 1.2 常见子工具

不同版本和授权下，VC Formal 的具体模块名称可能略有差异，但通常会包含下面这些能力：

- Base App：形式验证的基础入口，用于加载设计、约束、属性和运行环境。
- Assertion App：对 SVA 断言进行证明或反例分析，是最常用的功能之一。
- Connectivity App：检查模块端口、总线连接、位宽、未连接信号、误连等结构性问题。
- CDC App：跨时钟域分析，定位同步器缺失、单比特/多比特跨域风险、握手协议问题。
- RDC App：跨复位域分析，检查复位释放顺序、复位同步和复位毛刺风险。
- FSM App：状态机分析，识别死状态、无效转移、未覆盖状态和编码异常。
- Equivalence / ECO 相关能力：在修改后验证新旧版本行为一致，常用于修复后的回归确认。
- Coverage Analysis：分析形式覆盖率，帮助判断哪些状态、属性或路径还没有被证明到。
- Debug / Waveform 相关能力：查看反例、追踪路径、定位触发条件，方便把证明失败转回设计缺陷。

### 1.2.1 图中的工具速查
- FPV：功能形式验证，主要验证功能行为、协议约束和关键断言。
- SEQ：顺序相关分析，偏向序列行为、功耗分析和时序复用场景。
- FTA：Testbench Analyzer，检查测试平台本身是否有问题，避免仿真环境掩盖设计缺陷。
- DPV：Datapath Validation，验证数据通路、算术逻辑和组合路径是否符合预期。
- CC：Connectivity Checking，连通性检查，查端口是否接对、位宽是否匹配、有没有漏连或错连。
- FCA：Coverage Analyzer，覆盖率分析，判断哪些属性、状态或路径还未证明到。
- FXP：X-Propagation Verification，检查未知值 X 的传播风险。
- FSV：Hardware Security Verification，硬件安全验证，用于发现后门、非法状态和敏感控制路径风险。
- FRV：Customer Deliverables / Protocol Compliance，偏交付物检查和协议符合性验证。
- AEP：Auto Checks，自动检查类功能，适合批量规则确认。
- FLP：Low Power，低功耗验证，检查电源门控、隔离和唤醒逻辑。
- FuSa：Functional Safety，功能安全验证，面向安全关键设计和安全机制检查。

## 1.3 使用时的经验

- 先把约束写清楚，特别是时钟、复位、使能和环境假设，否则容易出现“证明了错误的问题”。
- 先从小范围、关键属性开始，再逐步扩展到完整模块。
- 对复杂设计优先检查接口协议和状态机，再做更深层的安全属性证明。
- 反例出来后不要只修断言，先判断是设计 bug、环境假设缺失，还是属性写得过强。

## 1.4 小结

VC Formal 的价值主要在于“早发现、深覆盖、可证明”。如果设计里有关键控制逻辑、跨时钟/跨复位路径或协议型接口，它通常比单纯仿真更有效。

## 1.5 Coverage Analyzer

Coverage Analyzer 的作用，是回答“这个设计还有哪些地方没有被证明到”以及“当前的形式验证结果是否足够完整”。它不是直接替代断言证明，而是站在覆盖率的角度，帮助你判断验证是否已经达到预期深度。

### 1.5.1 它解决什么问题

- 找出未覆盖的状态、路径、分支和属性。
- 判断某些证明失败是因为设计本身有问题，还是因为覆盖目标太深、约束不完整。
- 帮助从“能证明”走向“证明得完整”，避免只看少量已通过属性就过早收敛。
- 在复杂模块里定位验证盲区，例如某些状态机分支、异常返回路径、稀有握手场景。

### 1.5.2 常见输入与输出

- 输入通常包括设计、断言、约束、覆盖目标，以及前面各类验证运行产生的数据。
- 输出通常是覆盖报告，告诉你哪些目标已命中、哪些目标未命中、哪些路径可达但尚未证明。
- 在图里的流程中，Coverage Analyzer 会结合 VCS 侧的 merged.vdb 和 VC Formal 侧的 vcst_rtdb，再通过 URG 生成最终覆盖报告。

### 1.5.3 图里的流程怎么理解
- VCS Coverage flow 更偏仿真覆盖，先编译 DUT 和 TB，再跑多个测试，最后合并生成 merged.vdb。
- Formal Coverage Analyzer flow 更偏形式覆盖，先用 Tcl 读取设计、时钟、复位、网格和资源限制等信息，再进入 vcf shell 运行分析。
- formal 侧可以配合 exclusion file 排除已经明确不需要统计的内容，避免报告被噪声淹没。
- 最后由 URG 汇总不同来源的数据，产出统一的 coverage reports。
- 更详细的 URG 流程说明见 [URG 覆盖报告流程](URG.md)。

### 1.5.4 什么时候最有用

- 当断言已经通过，但你还不确定验证是否覆盖了关键边界时。
- 当设计很大、状态很多，需要知道验证工作是否集中在少数“容易命中”的路径上时。
- 当需要把仿真覆盖和形式覆盖结合起来做收敛判断时。
- 当你要对外说明验证质量，希望有更清晰的覆盖证据时。

### 1.5.5 使用时的注意点

- 覆盖率高不等于设计正确，必须结合断言证明和反例分析一起看。
- 约束太弱会导致覆盖目标看起来很多，但实际上没有意义。
- exclusion file 要谨慎使用，避免把真正应该检查的目标误排除。
- 对复杂设计，先看高价值目标，再逐步扩展到更细的覆盖项。

## 1.6 启动脚本

这段脚本是一个 FPV 启动和初始化脚本，核心作用是把设计、断言、时钟、复位和初始状态准备好，然后进入正式的形式验证流程。它的结构比较标准，先设模式，再读设计，再定义时钟和复位，最后做初始化。

```tcl
set_fml_appmode FPV

############################################################
## Setup Specific to DUT
############################################################
set design traffic
signoff_config -type (toggle)

############################################################
## Compile & Setup
############################################################
## Compilation Step
read_file -top $design -format sverilog -sva \
	-vcs {-f ../design/filelist +define+INLINE_SVA \
	../sva/traffic.sva}

## Clock Definitions
create_clock clk -period 100

## Reset Definitions
create_reset rst -sense high

## Initialisation Commands
sim_run -stable
sim_save_reset

#check_fv
```

### 1.6.1 逐行解读

- set_fml_appmode FPV：把 VC Formal 的工作模式切到 FPV，也就是功能形式验证。
- set design traffic：指定当前要分析的 DUT 是 traffic。
- signoff_config -type (toggle)：配置 signoff 相关策略，图里显示的是 toggle 类型设置。
- read_file -top $design -format sverilog -sva：读取顶层设计，并把 SVA 一起读进来。
- -vcs {-f ../design/filelist +define+INLINE_SVA ../sva/traffic.sva}：告诉工具用 VCS 风格的文件列表和宏定义来编译，同时把 traffic.sva 作为断言文件加入。
- create_clock clk -period 100：定义时钟 clk，周期是 100。
- create_reset rst -sense high：定义复位 rst，且为高有效。
- sim_run -stable：先让仿真/初始化状态稳定下来。
- sim_save_reset：保存 reset 状态，作为后续形式验证的起点之一。
- #check_fv：脚本末尾的注释标记，通常表示下一步进入正式检查。

### 1.6.2 这段脚本的执行顺序

- 先设置工具模式和 DUT。
- 再把 RTL 和断言文件一起编译进来。
- 接着定义 clock 和 reset，明确验证环境。
- 然后运行初始化步骤，保存可用于后续分析的初始状态。
- 最后进入 check_fv 一类的正式检查流程。

### 1.6.3 你可以怎么理解它

- 这段脚本本质上是在搭建一个最小可用的 FPV 环境。
- 前半段负责“把设计读进来”，后半段负责“把验证起点定下来”。
- 如果时钟、复位或者断言文件有问题，后面的证明结果通常都会失真，所以这部分是形式验证里最关键的准备阶段之一。
