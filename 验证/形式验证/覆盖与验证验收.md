# 覆盖率评估、验证质量与结果验收

> **第 18 册 · 工程交付**　主要依据 User Guide 第 20 章（第 836～913 页）、第 11 章（FCA）、第 21 章（FTA）及通用运行/调试章节。

## 1. 为什么不能只报告“全部属性通过”

形式验证的前提之一是必须有人编写有意义的属性。若一个仲裁器只检查“不存在两路同时授权”，这条性质即使被完整证明，也无法证明“有请求时必须给予授权”。因此验证验收需同时审查三个层面：属性是否正确、属性是否涵盖规格、证明是否完成。

### 1.1 四种互补的检查手段

- **方法：** 断言证明（FPV）

  **回答的问题：** 已编写规则是否永不违反

  **局限性：** 无法覆盖未编写的规格

- **方法：** 触发/行为覆盖（SVA cover）

  **回答的问题：** 关键事件是否可达

  **局限性：** 一条路径可达不代表全部情况正确

- **方法：** 代码覆盖与可达性（FCA）

  **回答的问题：** 未覆盖代码是否真的不可达

  **局限性：** 模型与约束可能过度限制

- **方法：** 属性敏感性（FTA）

  **回答的问题：** 注入错误能否被断言检测

  **局限性：** 故障集合有限、求解可能未完成

结合这些方法可以发现验证薄弱区域，但不能把它们的百分比相加为“验证完成度”。

## 2. 建立规格—属性对应表

- **规格项：** FIFO 上溢保护

  **类型：** 安全性

  **属性名称：**

  ```text
  AP_FIFO_DEPTH
  ```

  **输入前提：** `push` 为请求

  **覆盖目标：**

  ```text
  CP_FIFO_FULL
  ```

  **证明状态：** 待运行

  **评审状态：** 待评审

- **规格项：** 请求应答最多 3 拍

  **类型：** 有界响应

  **属性名称：**

  ```text
  AP_REQ_ACK
  ```

  **输入前提：** 合法请求被受理

  **覆盖目标：**

  ```text
  CP_REQ_ACCEPT
  ```

  **证明状态：** 待运行

  **评审状态：** 待评审

- **规格项：** 复位后中断清零

  **类型：** 初始化

  **属性名称：**

  ```text
  AP_RST_IRQ
  ```

  **输入前提：** 正确复位时序

  **覆盖目标：**

  ```text
  CP_RESET_RELEASE
  ```

  **证明状态：** 待运行

  **评审状态：** 待评审

这是交付模板，不是某次工具运行产生的真实状态。真实报告不应把未运行的规则写成 `Proven`。当规格中某项只能通过仿真、人工审查或系统测试验证时，要明确标注验证方式，而非制造一个看似覆盖它的空洞断言。

## 3. 验收需要保留哪些文件

```text
release/
├── manifest.yaml         # 设计与工具版本、校验和、资源配置
├── requirements.csv      # 规格与属性对应
├── assumptions.md        # 环境约束的来源和证明影响
├── properties.sv         # 提交时实际编译的 SVA
├── run.tcl               # 运行与初始化脚本
├── report_fv.txt         # 原始工具输出
├── summary.csv           # 属性状态汇总
├── waivers.md            # 豁免理由与审批
└── known_limits.md       # 未完成目标与后续验证计划
```

使用工具本身的 `save_session` 可保存调试数据，但不能替代可读的人类审核记录。运行结果需保留对应的源码版本和相关中间配置，避免以后找不到相同的证明环境。

## 4. 对“Proven”的独立复核

每条关键属性应检查：前件是否在某条合法路径上发生；`disable iff` 是否意外关闭主要检查阶段；假设有没有直接限制被验证的 DUT 内部状态；证明对象是否因黑盒化而改变；目标时钟和复位是否正确。建议将首次建立的属性在仿真中加入一两个故意错误版本，确认它确实能够检测到预期缺陷。

## 5. 不完成或豁免的处理要求

- **情况：**

  ```text
  Falsified
  ```

  **是否允许直接归类“通过”：** 否

  **必须补充的信息：** 反例分析、RTL/SVA/约束归因

- **情况：**

  ```text
  Inconclusive
  ```

  **是否允许直接归类“通过”：** 否

  **必须补充的信息：** 当前资源、证明难点、替代验证方案

- **情况：**

  ```text
  Disabled
  ```

  **是否允许直接归类“通过”：** 否

  **必须补充的信息：** 禁用依据及是否存在未覆盖规格

- **情况：**

  ```text
  Waived
  ```

  **是否允许直接归类“通过”：** 不能自动等同于通过

  **必须补充的信息：** 责任人、规格依据、审核和到期条件

- **情况：**

  ```text
  Uncoverable
  ```

  **是否允许直接归类“通过”：** 不是功能证明

  **必须补充的信息：** 约束可达性及覆盖目标定义

## 6. 组合使用 FCA 与 FTA

FCA 可优先帮助识别没有在正常运行配置下被触发的代码或状态；FTA 可进一步研究即便某区域可达，目前的断言是否能够检测改变。比如一个状态机的两个分支都可达，但错误地交换两路输出后当前断言仍不能发现，这显示需要更有针对性的输出行为属性。

## 7. 质量评审问题

1. 验证的 DUT 顶层和参数是否就是准备交付的版本？
2. 所有必检属性数量与规格表是否一致？
3. 属性是否均具有时钟、复位和输入前提说明？
4. 有无过度约束或从未触发的关键断言？
5. 所有失败与未完成是否已分类处理？
6. 自动生成的属性、覆盖目标及豁免是否经过审核？
7. 更改初始化脚本或工具版本后是否重新运行？
8. 有无保留完整的报告、运行命令及可重现文件？

## 8. 自动化结果摘要

如果需要脚本自动解析 `report_fv`，应优先采用该工具版本明确支持的机器可读输出，避免仅靠模糊匹配报告文本中的 `pass` 或 `fail`；结果里可能同时包含不同应用下的覆盖和断言状态。示例工程所附 `scripts/validate_sources.py` 只检查文件结构及代码示例，不是 VC Formal 报告解析器。
