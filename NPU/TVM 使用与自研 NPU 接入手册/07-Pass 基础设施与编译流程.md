# 07. Pass 基础设施与编译流程

> [!abstract] 本章内容
> 解释 ModulePass、FunctionPass、PassContext、Sequential、依赖与插桩。

## 一句话理解

每个 Pass 都应接收一种清楚的程序状态，产生另一种清楚的程序状态；完整编译是这些小变换按约定顺序组合。

## 核心要点

1. Pass 可以作用于模块、函数或更低层结构，并可声明所需前置变换。
2. `PassContext` 控制优化级别、配置、禁用项和插桩。
3. `Sequential` 让项目定义自己的可审计流水，而不是依赖隐式默认顺序。
4. 分析结果应有明确失效规则，程序被改写后不能继续使用过期信息。
5. NPU 分区通常放在通用规范化之后、可能破坏组合结构的融合之前。

    A["输入程序状态"] --> B["分析信息"]

## 逐项解析

### 1. Pass 可以作用于模块、函数或更低层结构

Pass 可以作用于模块、函数或更低层结构，并可声明所需前置变换。

阅读时先定位产生该信息的函数，再查找消费它的下一阶段。把两处代码和中间 IR 放在一起观察，比单独记忆类名更容易理解。

**实现建议：** 为流水各阶段命名并输出 IR 快照散列值。

> [!warning] 本小节常见问题
> Pass 顺序改变可能使匹配数量变化，不能只看每个 Pass 的局部测试。

### 2. `PassContext` 控制优化级别、配置、禁用项和插桩。

`PassContext` 控制优化级别、配置、禁用项和插桩。

把变换前后的 IR 并排比较，重点查看函数参数、调用、属性、StructInfo 和返回值。只记录最终 IR 会丢失变化发生的位置。

**实现建议：** 自定义 Pass 在空模块、无匹配、动态尺寸和重复执行时都应稳定。

> [!warning] 本小节常见问题
> 在全局可变对象中保存分析结果会污染并行编译。

### 3. `Sequential` 让项目定义自己的可审计流水

`Sequential` 让项目定义自己的可审计流水，而不是依赖隐式默认顺序。

实现时将硬件固定限制放入 Target 或能力文件，把用户可选策略放入编译配置；二者发生冲突时应报告具体字段。

**实现建议：** 用 PassInstrument 记录耗时、IR 大小和外部函数数量。

> [!warning] 本小节常见问题
> 把所有工作塞进一个大型 Pass 会使定位、复用和单测都变困难。

### 4. 分析结果应有明确失效规则

分析结果应有明确失效规则，程序被改写后不能继续使用过期信息。

测试至少包含一个正常样本和一个只改变单一条件的反向样本。这样，结构或结果变化时能直接找到对应规则。

**实现建议：** 把接入流程写成一个可调用编译流程，供 CLI、测试和服务共用。

> [!warning] 本小节常见问题
> Pass 顺序改变可能使匹配数量变化，不能只看每个 Pass 的局部测试。

### 5. NPU 分区通常放在通用规范化之后、可能破坏组合结构的融合之前。

NPU 分区通常放在通用规范化之后、可能破坏组合结构的融合之前。

保存可由工具读取的阶段报告，其中包含输入摘要、输出摘要、Pass 配置、Target、耗时和错误；文本日志用于辅助阅读。

**实现建议：** 为流水各阶段命名并输出 IR 快照散列值。

> [!warning] 本小节常见问题
> 在全局可变对象中保存分析结果会污染并行编译。

## 设计评审问题

1. 本阶段接收哪一种 IR，要求哪些属性已经存在？
2. 本阶段产生哪些新函数、属性、常量或模块？
3. 遇到不被支持的输入时，是保留给其他后端、报告编译错误，还是插入转换？
4. 哪些配置属于硬件固定限制，哪些配置允许自动搜索？
5. 如何证明重复执行本阶段不会产生额外变化？
6. 如何在日志中解释每个重要决定？

### 07.A 本节要解决的具体问题

编写一个只给模块增加版本属性的模块 Pass，并使用 `Sequential` 与内置 Pass 组合。这个例子用来理解 Pass 信息、执行顺序和上下文配置。

这类小例子的价值在于变量少、输出可直接观察。第一次运行时不要同时加入图改写、外部代码生成和真实设备执行；先确认当前层的输入与输出，再增加下一层。建议为本例新建独立目录，保存命令、标准输出、IR、编译产物摘要和环境信息。

### 07.B 示例一：最小可观察输入

**官方依据：** [Pass 基础设施](https://tvm.apache.org/docs/arch/pass_infra.html) 与 [Relax 变换教程](https://tvm.apache.org/docs/deep_dive/relax/tutorials/relax_transformation.html)。

**v0.24.0 源码位置：** `docs/arch/pass_infra.rst`、`include/tvm/ir/transform.h`、`src/ir/transform.cc`。

```python
import tvm
from tvm import relax

@tvm.transform.module_pass(opt_level=0, name="AttachBackendRevision")
class AttachBackendRevision:
    def transform_module(self, mod, ctx):
        return mod.with_attr("acme_npu.revision", "npu-v1")

pipeline = tvm.transform.Sequential(
    [
        AttachBackendRevision(),
        relax.transform.FoldConstant(),
        relax.transform.DeadCodeElimination(),
    ]
)
# result = pipeline(input_mod)
```

按以下顺序执行：

1. 在新进程中确认 `tvm.__file__`、动态库路径和 TVM 提交，避免受到旧进程注册状态影响；
2. 复制示例到单独文件，只补充示例明确要求的输入对象，不先加入额外优化；
3. 执行后保存完整输出；若生成 IR，同时保存 `script(show_meta=True)` 的文本；
4. 把输出与下面的预期现象逐项比较，不以“没有抛出异常”代替功能检查；
5. 重复执行一次并比较主要产物，确认结果没有依赖临时全局状态或未固定的遍历顺序。

> [!success] 预期现象
> Pass 不应就地修改输入模块中可共享的对象；输出模块带新增属性。`Sequential` 保留明确顺序，后一个 Pass 能看到前一个 Pass 的结果。调试时应在每个 Pass 前后保存模块摘要。

> [!tip] 如何阅读输出
> 先看对象类型和函数数量，再看属性、调用形式、形状与数据类型，最后看运行结果或编译产物。若前一项不符合预期，先停止后续步骤。这样能把问题限定在最早出现差异的阶段。

### 07.C 示例二：只改变一个条件

交换常量折叠与自定义改写的顺序，构造一个只有在常量折叠前才能识别的模式。比较两种顺序的输出，确认变换依赖应写进组合流程而非留给偶然顺序。

执行第二个例子时，复制第一个例子的输入与环境，只修改上文指出的一项。把两个输出做结构比较，并写下以下四个答案：

1. 第一次出现差异的是哪一个阶段？
2. 差异表现为函数、属性、形状、数据类型、编译产物还是运行结果？
3. 当前行为是明确拒绝、交给其他后端执行，还是编译错误？
4. 日志是否足以让另一位开发者不查看本次进程状态也能复现？

如果同时观察到多个变化，应把第二个例子继续拆小。教程中的成功示例说明“怎样走通”，而单条件变化说明“系统为何作出这个决定”，两者缺一不可。

### 07.D 改造成自研 NPU 示例

NPU 分区 Pass 应明确所需前置变换和后续处理。使用 Pass Instrument 记录模型散列、Target、Pass 名称、函数数量与耗时，异常时保留最后一个成功模块。

改造时建议保留三份相互独立的输入：最小 Relax 或 TensorIR、设备编译器输入、运行时调用输入。三份输入使用同一个样本编号，并记录转换前后的关键字段。这样可以分别测试 TVM 变换、NPU 编译器和驱动，不需要每次都运行完整模型。

至少补充以下样本：

- 一个完全满足能力要求的正向样本；
- 一个只改变数据类型的反向样本；
- 一个只改变形状或属性的反向样本；
- 一个包含主机与 NPU 混合执行的样本；
- 一个导出后在新进程加载的样本；
- 若支持动态尺寸，再增加最小值、常用值和最大值附近的样本。
