# 11. 源码构建与第一个程序

> [!abstract] 本章内容
> 给出 Linux 上的源码构建、环境确认、最小 Relax 模型、编译、运行和排错步骤。

## 一句话理解

首次构建的目标是建立可信工具环境，不是立即打开所有后端；最小配置稳定后再逐项增加自研模块。

## 核心要点

1. v0.24.0 要求 CMake 3.24 或更高版本、Python 3.10 或更高版本，并建议 LLVM 15 或更新版本。
2. 使用 SSH 与 `--recursive` 取得源码，确保子模块与主仓库提交一致。
3. `config.cmake` 决定编译器、运行时和第三方后端是否进入动态库。
4. `tvm-ffi` 与 TVM Python 包都必须指向当前构建。
5. 最小程序应覆盖创建 IRModule、运行 pipeline、编译、建立 VM 和读取结果。

## 逐项解析

### 1. v0.24.0 要求 CMake 3.24 或更高版本、Python 3.10 或更高版本

v0.24.0 要求 CMake 3.24 或更高版本、Python 3.10 或更高版本，并建议 LLVM 15 或更新版本。 这一点之所以重要，是因为 TVM 的信息会在多个 IR 层次之间逐步变得具体。上一层没有保留下来的信息，下一层通常无法可靠恢复；下一层过早写死的选择，也会限制后续优化。初学时应在每次变换前后打印模块，找出函数、调用、属性、形状和 dtype 的变化。

实现时可执行的动作是：使用 `git clone --recursive git@github.com:apache/tvm.git` 并切到固定 tag。 建议同时保存输入 IR、输出 IR、Pass 配置、Target 和日志。若出现结果差异，先找到第一次发生结构变化的阶段，再向下检查，而不是从最终设备结果反推全部过程。

> [!warning] 本小节常见问题
> 系统中多个 `libtvm` 并存时，Python 可能加载到旧库。

### 2. 使用 SSH 与 `--recursive` 取得源码

使用 SSH 与 `--recursive` 取得源码，确保子模块与主仓库提交一致。 这一点之所以重要，是因为 TVM 的信息会在多个 IR 层次之间逐步变得具体。上一层没有保留下来的信息，下一层通常无法可靠恢复；下一层过早写死的选择，也会限制后续优化。初学时应在每次变换前后打印模块，找出函数、调用、属性、形状和 dtype 的变化。

实现时可执行的动作是：先启用 LLVM，关闭暂时不用的 GPU 与外部库。 建议同时保存输入 IR、输出 IR、Pass 配置、Target 和日志。若出现结果差异，先找到第一次发生结构变化的阶段，再向下检查，而不是从最终设备结果反推全部过程。

> [!warning] 本小节常见问题
> 遗漏子模块有时到链接阶段才报错。

### 3. `config.cmake` 决定编译器、运行时和第三方后端是否进入动态库。

`config.cmake` 决定编译器、运行时和第三方后端是否进入动态库。 这一点之所以重要，是因为 TVM 的信息会在多个 IR 层次之间逐步变得具体。上一层没有保留下来的信息，下一层通常无法可靠恢复；下一层过早写死的选择，也会限制后续优化。初学时应在每次变换前后打印模块，找出函数、调用、属性、形状和 dtype 的变化。

实现时可执行的动作是：运行 `tvm.support.libinfo()` 保存实际构建信息。 建议同时保存输入 IR、输出 IR、Pass 配置、Target 和日志。若出现结果差异，先找到第一次发生结构变化的阶段，再向下检查，而不是从最终设备结果反推全部过程。

> [!warning] 本小节常见问题
> 把目标设备交叉编译器设为构建 TVM 本体的 C++ 编译器，通常不是所需做法。

## 设计评审问题

1. 本阶段接收哪一种 IR，要求哪些属性已经存在？
2. 本阶段产生哪些新函数、属性、常量或模块？
3. 遇到不被支持的输入时，是保留给其他后端、报告编译错误，还是插入转换？
4. 哪些配置属于硬件固定限制，哪些配置允许自动搜索？
5. 如何证明重复执行本阶段不会产生额外变化？
6. 如何在日志中解释每个重要决定？

## 章末小结

本章的重点不是记住所有类名，而是明确输入状态、处理动作、输出状态和失败处理。接入自研 NPU 时，每一层都应保留可检查的中间结果，使图分区、代码生成、设备提交和数值对照可以分别验证。
