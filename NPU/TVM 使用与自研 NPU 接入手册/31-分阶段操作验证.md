## 31.1 验证项：固定源码与确认构建

> [!abstract] 目标
> 使用 SSH 取得 v0.24.0，完成最小 LLVM 构建，并证明 Python 加载当前动态库。

### 准备

Linux、Git SSH 权限、CMake 3.24+、Python 3.10+、LLVM 15+。

开始前建立独立工作目录，记录源码提交、构建类型、CMake 选项、Python 包路径、LLVM 版本和目标设备版本。所有命令应能从干净终端重新执行。

### 操作

克隆 `git@github.com:apache/tvm.git`；切到 `v0.24.0`；复制 `config.cmake`；启用 LLVM；构建；安装 tvm-ffi；以 editable 方式安装 Python 包。

每完成一个动作后保存对应的 IR、JSON、命令反汇编或运行日志。若验证项包含设备执行，应固定随机种子并保存输入，不要只保存最终统计数字。

### 预期观察

`git rev-parse HEAD`、`tvm.__file__`、`tvm.base._LOADED_LIBS` 与 `tvm.support.libinfo()` 指向同一构建。

将预期写成自动断言。结构使用 `tvm.ir.assert_structural_equal`，数值按算子规格说明选择位级比较或误差比较，模块加载在新进程完成，性能使用预热与多次重复。

### 失败排查

若提交号正确但库路径错误，先清理 Python 环境中的旧 TVM 包，而不是修改源码。

排查顺序固定为：输入与环境 → 导入后 Relax → 分区后 Relax → 外部产物 → 模块加载 → Tensor 绑定 → 命令 → 设备状态 → 输出。找到第一次偏离预期的位置后再深入。

## 实现说明与验证步骤

> [!note] 依据与适用范围
> 本节依据所列 Apache TVM 官方资料和 v0.24.0 源码整理，给出输入条件、操作步骤、预期结果、异常处理和自研 NPU 适配要求。接口细节以固定版本源码与测试为准，在线页面用于补充说明。

### 31.A 目标与适用范围

每次验证只改变一个条件，并保存输入、命令、关键输出和结论。下面的记录格式可以直接用于本章全部验证项。

参考样本保持输入规模较小，以便直接检查对象、字段和输出。首次执行时不要同时加入图改写、外部代码生成和真实设备执行；应先确认当前阶段的输入与输出，再增加后续处理。建议为该项验证建立独立目录，保存命令、标准输出、IR、编译产物摘要和环境信息。

### 31.B 参考实现

**官方依据：** [快速开始](https://tvm.apache.org/docs/get_started/tutorials/quick_start.html)、[导入模型](https://tvm.apache.org/docs/how_to/tutorials/import_model.html) 与 [BYOC 教程](https://tvm.apache.org/docs/how_to/tutorials/bring_your_own_codegen.html)。

**v0.24.0 源码位置：** `docs/get_started/tutorials/`、`docs/how_to/tutorials/`、`tests/python/relax/`。

```yaml
experiment: 07_partition_matmul_relu
baseline:
  tvm_commit: af3e4ba
  target: llvm
change:
  pass: FuseOpsByPattern
  backend: acme_npu
inputs:
  shape_x: [2, 4]
  shape_w: [4, 8]
  dtype: float32
expected:
  external_functions: 1
  host_matmul_calls: 0
artifacts:
  - before.py
  - after.py
  - report.json
```

按以下顺序执行：

1. 在新进程中确认 `tvm.__file__`、动态库路径和 TVM 提交，避免受到旧进程注册状态影响；
2. 将参考实现保存到单独文件，只补充本节明确要求的输入对象，不先加入额外优化；
3. 执行后保存完整输出；若生成 IR，同时保存 `script(show_meta=True)` 的文本；
4. 把输出与下面的预期现象逐项比较，不以“没有抛出异常”代替功能检查；
5. 重复执行一次并比较主要产物，确认结果没有依赖临时全局状态或未固定的遍历顺序。

> [!success] 预期现象
> 记录中既有基准，也有本次唯一变化。预期结果是可自动检查的数量或字段，不只写“成功”。文件名稳定后可以批量比较多次运行。

> [!tip] 输出检查顺序
> 先看对象类型和函数数量，再看属性、调用形式、形状与数据类型，最后看运行结果或编译产物。若前一项不符合预期，先停止后续步骤。这样能把问题限定在最早出现差异的阶段。

### 31.C 单项条件验证

执行条件变化样本时，复制参考实现的输入与环境，只修改上文指出的一项。对两个输出进行结构比较，并记录以下四项：

1. 第一次出现差异的是哪一个阶段？
2. 差异表现为函数、属性、形状、数据类型、编译产物还是运行结果？
3. 当前行为是明确拒绝、交给其他后端执行，还是编译错误？
4. 日志是否足以让另一位开发者不查看本次进程状态也能复现？

如果同时观察到多个变化，应继续缩小条件变化样本。参考实现用于确认正常处理，单项条件验证用于确认系统为何接受、拒绝或转交当前输入。

### 31.D 自研 NPU 适配要求
