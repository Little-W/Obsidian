# 07. Pass 基础设施与编译流水

> [!abstract] 本章内容
> 解释 ModulePass、FunctionPass、PassContext、Sequential、依赖与插桩。

## 一句话理解

每个 Pass 都应接收一种清楚的程序状态，产生另一种清楚的程序状态；完整编译是这些小变换按约定顺序组合。

## 核心要点

1. Pass 可以作用于模块、函数或更低层结构，并可声明所需前置变换。
2. `PassContext` 控制优化级别、配置、禁用项和插桩。
3. `Sequential` 让项目定义自己的可审计流水，而不是依赖隐式默认顺序。
4. 分析结果应有明确失效规则，程序被改写后不能继续使用过期信息。
5. NPU 分区通常放在通用规范化之后、可能破坏组合结构的融合之前。

    A["输入程序状态"] --> B["分析信息"]
    B --> C["本章所述处理"]
    C --> D["输出程序状态"]
    D --> E["日志与可复现记录"]

## 逐项解析

### 1. Pass 可以作用于模块、函数或更低层结构

Pass 可以作用于模块、函数或更低层结构，并可声明所需前置变换。 这一点之所以重要，是因为 TVM 的信息会在多个 IR 层次之间逐步变得具体。上一层没有保留下来的信息，下一层通常无法可靠恢复；下一层过早写死的选择，也会限制后续优化。初学时应在每次变换前后打印模块，找出函数、调用、属性、形状和 dtype 的变化。

实现时可执行的动作是：为流水各阶段命名并输出 IR 快照散列值。 建议同时保存输入 IR、输出 IR、Pass 配置、Target 和日志。若出现结果差异，先找到第一次发生结构变化的阶段，再向下检查，而不是从最终设备结果反推全部过程。

> [!warning] 本小节常见问题
> Pass 顺序改变可能使匹配数量变化，不能只看每个 Pass 的局部测试。

### 2. `PassContext` 控制优化级别、配置、禁用项和插桩。

`PassContext` 控制优化级别、配置、禁用项和插桩。 这一点之所以重要，是因为 TVM 的信息会在多个 IR 层次之间逐步变得具体。上一层没有保留下来的信息，下一层通常无法可靠恢复；下一层过早写死的选择，也会限制后续优化。初学时应在每次变换前后打印模块，找出函数、调用、属性、形状和 dtype 的变化。

实现时可执行的动作是：自定义 Pass 在空模块、无匹配、动态尺寸和重复执行时都应稳定。 建议同时保存输入 IR、输出 IR、Pass 配置、Target 和日志。若出现结果差异，先找到第一次发生结构变化的阶段，再向下检查，而不是从最终设备结果反推全部过程。

> [!warning] 本小节常见问题
> 在全局可变对象中保存分析结果会污染并行编译。

### 3. `Sequential` 让项目定义自己的可审计流水

`Sequential` 让项目定义自己的可审计流水，而不是依赖隐式默认顺序。 这一点之所以重要，是因为 TVM 的信息会在多个 IR 层次之间逐步变得具体。上一层没有保留下来的信息，下一层通常无法可靠恢复；下一层过早写死的选择，也会限制后续优化。初学时应在每次变换前后打印模块，找出函数、调用、属性、形状和 dtype 的变化。

实现时可执行的动作是：用 PassInstrument 记录耗时、IR 大小和外部函数数量。 建议同时保存输入 IR、输出 IR、Pass 配置、Target 和日志。若出现结果差异，先找到第一次发生结构变化的阶段，再向下检查，而不是从最终设备结果反推全部过程。

> [!warning] 本小节常见问题
> 把所有工作塞进一个大型 Pass 会使定位、复用和单测都变困难。

### 4. 分析结果应有明确失效规则

分析结果应有明确失效规则，程序被改写后不能继续使用过期信息。 这一点之所以重要，是因为 TVM 的信息会在多个 IR 层次之间逐步变得具体。上一层没有保留下来的信息，下一层通常无法可靠恢复；下一层过早写死的选择，也会限制后续优化。初学时应在每次变换前后打印模块，找出函数、调用、属性、形状和 dtype 的变化。

实现时可执行的动作是：把接入流程写成一个可调用 pipeline，供 CLI、测试和服务共用。 建议同时保存输入 IR、输出 IR、Pass 配置、Target 和日志。若出现结果差异，先找到第一次发生结构变化的阶段，再向下检查，而不是从最终设备结果反推全部过程。

> [!warning] 本小节常见问题

### 5. NPU 分区通常放在通用规范化之后、可能破坏组合结构的融合之前。

## 实施清单

- [ ] 为流水各阶段命名并输出 IR 快照散列值。
- [ ] 自定义 Pass 在空模块、无匹配、动态尺寸和重复执行时都应稳定。
- [ ] 用 PassInstrument 记录耗时、IR 大小和外部函数数量。
- [ ] 把接入流程写成一个可调用 pipeline，供 CLI、测试和服务共用。

## 设计评审问题

1. 本阶段接收哪一种 IR，要求哪些属性已经存在？
2. 本阶段产生哪些新函数、属性、常量或模块？
3. 遇到不被支持的输入时，是保留给其他后端、报告编译错误，还是插入转换？
4. 哪些配置属于硬件固定限制，哪些配置允许自动搜索？
5. 如何证明重复执行本阶段不会产生额外变化？
6. 如何在日志中解释每个重要决定？

## 章末小结

本章的重点不是记住所有类名，而是明确输入状态、处理动作、输出状态和失败处理。接入自研 NPU 时，每一层都应保留可检查的中间结果，使图分区、代码生成、设备提交和数值对照可以分别验证。
