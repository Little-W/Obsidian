# 13. DLight MetaSchedule 与性能调优

> [!abstract] 本章内容
> 对比规则调度与搜索调度，说明任务提取、候选构建、设备测量、数据库和结果复用。

## 功能概述

DLight 快速给出合理方案，MetaSchedule 用更多编译与测量时间寻找更快方案；两者都建立在正确的 TensorIR 与可信测量之上。

## 核心要点

1. DLight 适合快速基线和未调优任务的默认处理。
2. MetaSchedule 由任务、TuneContext、空间生成器、搜索策略、代价模型、Builder、Runner 和数据库组成。
3. 数据库保存工作负载结构、调度 trace 与测量时间。
4. RPC Runner 可在远程设备执行候选，主机负责生成和编译。
5. 自研 NPU 若采用 BYOC 图编译，可在自研编译器内部调优，也可为 TIR 路线增加规则。

## 详细说明

### 1. DLight 适合快速基线和未调优任务的默认处理。

**实现建议：** 先验证每个候选的数值，再纳入性能比较。

> [!warning] 本小节常见问题
> 候选在主机上编译成功不表示 NPU 固件接受命令。

### 2. MetaSchedule 由任务、TuneContext、空间生成器、搜索策略、代价模型、Builder、Runner 和数据库组成。

MetaSchedule 由任务、TuneContext、空间生成器、搜索策略、代价模型、Builder、Runner 和数据库组成。

把变换前后的 IR 并排比较，重点查看函数参数、调用、属性、StructInfo 和返回值。只记录最终 IR 会丢失变化发生的位置。

**实现建议：** 测量前预热并使用多次重复，保存分布而非单个最小值。

> [!warning] 本小节常见问题
> 使用旧数据库但不核对硬件版本会得到无效调度。

### 3. 数据库保存工作负载结构、调度 trace 与测量时间。

数据库保存工作负载结构、调度 trace 与测量时间。

实现时将硬件固定限制放入 Target 或能力文件，把用户可选策略放入编译配置；二者发生冲突时应报告具体字段。

**实现建议：** 数据库键加入硬件、固件、编译器和目标配置版本。

> [!warning] 本小节常见问题
> 测量时间包含日志打印时，排序结果可能反映日志量而非计算速度。

### 4. RPC Runner 可在远程设备执行候选

RPC Runner 可在远程设备执行候选，主机负责生成和编译。

测试至少包含一个正常样本和一个只改变单一条件的反向样本。这样，结构或结果变化时能直接找到对应规则。

**实现建议：** 对未找到记录的任务提供基础调度或主机处理。

> [!warning] 本小节常见问题
> 候选在主机上编译成功不表示 NPU 固件接受命令。

### 5. 自研 NPU 若采用 BYOC 图编译

自研 NPU 若采用 BYOC 图编译，可在自研编译器内部调优，也可为 TIR 路线增加规则。

保存可由工具读取的阶段报告，其中包含输入摘要、输出摘要、Pass 配置、Target、耗时和错误；文本日志用于辅助阅读。

**实现建议：** 把片上容量、指令限制和对齐要求写入候选生成。

## 实现说明与验证步骤

> [!note] 依据与适用范围
> 本节依据所列 Apache TVM 官方资料和 v0.24.0 源码整理，给出输入条件、操作步骤、预期结果、异常处理和自研 NPU 适配要求。接口细节以固定版本源码与测试为准，在线页面用于补充说明。

### 13.A 目标与适用范围

对同一模块分别使用规则调度和搜索调优，并记录编译时间、数据库内容和设备时间。两种方法解决的问题相近，但成本与可重复性不同。

参考样本保持输入规模较小，以便直接检查对象、字段和输出。首次执行时不要同时加入图改写、外部代码生成和真实设备执行；应先确认当前阶段的输入与输出，再增加后续处理。建议为该项验证建立独立目录，保存命令、标准输出、IR、编译产物摘要和环境信息。

### 13.B 参考实现

**官方依据：** [自定义优化](https://tvm.apache.org/docs/how_to/tutorials/customize_opt.html)、[DLight](https://tvm.apache.org/docs/deep_dive/tensor_ir/tutorials/dlight_gpu_scheduling.html) 与 [MetaSchedule](https://tvm.apache.org/docs/deep_dive/tensor_ir/tutorials/meta_schedule.html)。

**v0.24.0 源码位置：** `docs/how_to/tutorials/customize_opt.py`、`python/tvm/s_tir/dlight/`、`python/tvm/s_tir/meta_schedule/`。

```python
import tvm
from tvm import relax

def prepare_for_tuning(mod):
    return tvm.transform.Sequential(
        [
            relax.transform.LegalizeOps(),
            relax.transform.AnnotateTIROpPattern(),
            relax.transform.FoldConstant(),
            relax.transform.FuseOps(),
            relax.transform.FuseTIR(),
        ]
    )(mod)

# lowered = prepare_for_tuning(mod)
# 后续可选择 DLight 默认规则，或 MetaSchedule 数据库。
```

按以下顺序执行：

1. 在新进程中确认 `tvm.__file__`、动态库路径和 TVM 提交，避免受到旧进程注册状态影响；
2. 将参考实现保存到单独文件，只补充本节明确要求的输入对象，不先加入额外优化；
3. 执行后保存完整输出；若生成 IR，同时保存 `script(show_meta=True)` 的文本；
4. 把输出与下面的预期现象逐项比较，不以“没有抛出异常”代替功能检查；
5. 重复执行一次并比较主要产物，确认结果没有依赖临时全局状态或未固定的遍历顺序。

> [!success] 预期现象
> 调优前必须先得到可调度的 TIR 函数。规则调度编译快，适合建立基准；搜索调优需要工作目录、测量设备和试验预算，最终结果必须与数据库和 Target 一起保存。

> [!tip] 输出检查顺序
> 先看对象类型和函数数量，再看属性、调用形式、形状与数据类型，最后看运行结果或编译产物。若前一项不符合预期，先停止后续步骤。这样能把问题限定在最早出现差异的阶段。

### 13.C 单项条件验证

用极小试验预算和较大试验预算处理同一任务，比较最佳记录、编译时间和设备时间。不要把教程中的小预算误当成产品参数。

执行条件变化样本时，复制参考实现的输入与环境，只修改上文指出的一项。对两个输出进行结构比较，并记录以下四项：

1. 第一次出现差异的是哪一个阶段？
2. 差异表现为函数、属性、形状、数据类型、编译产物还是运行结果？
3. 当前行为是明确拒绝、交给其他后端执行，还是编译错误？
4. 日志是否足以让另一位开发者不查看本次进程状态也能复现？

如果同时观察到多个变化，应继续缩小条件变化样本。参考实现用于确认正常处理，单项条件验证用于确认系统为何接受、拒绝或转交当前输入。

### 13.D 自研 NPU 适配要求

BYOC 已接纳的子图由 NPU 编译器优化，剩余 TIR 才交给 DLight 或 MetaSchedule。任务提取报告应区分外部函数与 TVM 内核，避免为不会执行的函数浪费测量时间。

改造时建议保留三份相互独立的输入：最小 Relax 或 TensorIR、设备编译器输入、运行时调用输入。三份输入使用同一个样本编号，并记录转换前后的关键字段。这样可以分别测试 TVM 变换、NPU 编译器和驱动，不需要每次都运行完整模型。

至少补充以下样本：

- 一个完全满足能力要求的正向样本；
- 一个只改变数据类型的反向样本；
- 一个只改变形状或属性的反向样本；
- 一个包含主机与 NPU 混合执行的样本；
- 一个导出后在新进程加载的样本；
- 若支持动态尺寸，再增加最小值、常用值和最大值附近的样本。
