## 摘要

在过去三年中，最大的稠密深度学习模型增长了 1000 倍以上，达到数千亿参数，而 GPU 内存仅增长了 5 倍（从 16 GB 到 80 GB）。因此，模型规模的增长主要依靠系统创新来支撑，这些创新使大型模型能够放入多块 GPU 的聚合 GPU 内存中。然而，我们正在接近 GPU 内存墙。仅仅为了容纳一个万亿参数模型进行训练，就需要 800 块 NVIDIA V100 GPU，而这样的集群对于大多数数据科学家来说根本难以获得。此外，在这种规模上训练模型需要复杂地组合多种并行技术，这给数据科学家带来了巨大的模型重构负担。

在本文中，我们提出==ZeRO-Infinity，这是一种新的异构系统技术，它利用 GPU、CPU 和 NVMe 内存，使得在有限资源上支持前所未有的模型规模成为可能，同时不需要重构模型代码。与此同时，它能够实现出色的训练吞吐量和可扩展性，不受 CPU 或 NVMe 带宽限制的束缚。==ZeRO-Infinity 可以在当前一代 GPU 集群上容纳具有数十万亿甚至数百万亿参数的模型进行训练。它也可以在单个 NVIDIA DGX-2 节点上微调万亿参数模型，使大型模型更加易于使用。在训练吞吐量和可扩展性方面，它在 512 块 NVIDIA V100 GPU 上持续达到超过 25 petaflops（峰值的 40%），同时还展示出超线性扩展能力。ZeRO-Infinity 的开源实现可通过 DeepSpeed[^1] 获得。

## 1 扩展引言

近年来，深度学习（DL）取得了巨大进展，从支撑搜索引擎到支撑智能家居虚拟助手，它已经成为我们生活中不可或缺的一部分。模型规模的增大处于这些进展的核心位置 [1-3]，多项研究表明这种趋势还将继续 [4, 5]。因此，人们在训练巨大模型方面进行了大量投入。

在过去三年中，深度学习中已经训练的最大稠密模型从一亿参数（ELMo [6]）增长到超过一千亿参数（GPT-3 [4]），增长超过 1000 倍。相比之下，单块 GPU 的内存只增加了很小的 5 倍（16 GB 到 80 GB）。因此，模型规模的增长主要是通过大规模 DL 模型训练系统技术的进步实现的，其中模型并行 [7]、流水线并行 [8-10] 和 ZeRO [11, 12] 等并行技术为训练更大、更强的模型开辟了道路。

当前大模型训练技术的最先进方法是三维并行（3D parallelism [13, 14]），它将模型并行（张量切分）和流水线并行与数据并行相结合，从而在数百或数千块 GPU 上高效地将 DL 训练扩展到万亿参数规模。例如，DeepSpeed 的 3D 并行实现能够通过充分利用集群聚合 GPU 内存，在 800 块 NVIDIA V100 GPU 上扩展到超过一万亿参数 [15]。

尽管 3D 并行具备大模型训练能力，但我们现在正在到达 GPU 内存墙 [16]。聚合 GPU 内存已经不足以支撑模型规模的继续增长。即使使用最新的 NVIDIA A100 GPU（80 GB 内存），3D 并行也需要 320 块 GPU 才能仅仅容纳一个万亿参数模型进行训练；而要扩展到未来的一百万亿参数模型，即便假设未来几年 GPU 内存再增加 5 倍，也需要超过 6000 块 GPU。我们已经无法再以 GPU 内存作为瓶颈来持续支撑模型规模增长。

GPU 内存墙还限制了数据科学家访问甚至是今天的大模型，尤其是在微调场景中。大模型首先在大量通用数据上进行预训练，然后通过微调，同一个模型可以专门适配各种应用。尽管预训练一个拥有数千亿参数的模型可能需要数百万 GPU 计算小时，但微调要便宜得多，所需的 GPU 计算小时显著更少，并且可以在带有少量 GPU 的单个计算节点上完成。虽然许多企业和用户可以获得这种计算资源，但它们不幸地受到这些计算节点上可用内存的限制，而内存限制又限制了可微调模型的大小。这使得大模型微调对于无法访问大型 GPU 集群的大多数研究人员和公司来说仍然不可及。例如，使用 3D 并行微调 GPT-3 仅仅为了容纳模型进行训练就需要超过 8 个 DGX-2 节点（128 块 GPU），尽管单个 DGX-2 节点（16 块 GPU）已经具备在合理时间内微调它所需的计算能力。

除了 GPU 内存墙之外，训练超大模型的最先进方法在可用性和灵活性方面也受到限制。如上所述，3D 并行需要以复杂方式组合数据并行、模型并行和流水线并行，才能达到数千亿或数万亿参数。虽然这样的系统可以非常高效，但它要求数据科学家进行大量模型代码重构，用张量切分版本替换单 GPU 算子，并将模型拆分成负载均衡的流水线阶段。这也使 3D 并行在支持的模型类型上缺乏灵活性。具有复杂依赖关系的模型难以转换为负载均衡的流水线。

鉴于大模型训练的整体背景，出现了三个问题：

- 展望未来，我们如何支持模型规模接下来的 1000 倍增长，从类似 GPT-3 的 1750 亿参数模型走向拥有数百万亿参数的模型？
- 我们如何让今天的大模型能够被更多无法访问数百块 GPU 的数据科学家使用？
- 我们能否通过消除模型重构和多种并行形式的需求，使大模型训练更容易？

在本文中，我们从 3D 并行向前迈出一大步，提出 ZeRO-Infinity，这是一个能够解决上述所有大模型训练挑战的新系统。

**前所未有的模型规模。** ZeRO-Infinity 通过一种名为==infinity offload engine（无限卸载引擎）==的异构内存访问新创新，扩展了 ZeRO 系列技术 [11, 12]。这使 ZeRO-Infinity 能够同时利用 CPU 和 NVMe 内存，在有限 GPU 资源上支持巨大模型规模。此外，ZeRO-Infinity 还引入了一种新的 GPU 内存优化技术，称为 ==memory-centric tiling（以内存为中心的分块）==，用于支持极大的单个层，否则这些层即使一次只处理一层也无法放入 GPU 内存。借助 infinity offload engine 和 memory-centric tiling，ZeRO-Infinity 不仅支持模型规模接下来的 1000 倍增长，还使具有有限 GPU 资源的数据科学家也能使用大模型。

**出色的训练效率。** ZeRO-Infinity 引入了一种新的数据划分策略，用于==利用所有设备上的聚合内存带宽，我们称之为 bandwidth-centric partitioning（以带宽为中心的划分）==；它还结合了强大的以通信重叠为中心的设计，以及 infinity offload engine 中针对高性能 NVMe 访问的优化。综合起来，尽管将数据卸载到 CPU 或 NVMe，ZeRO-Infinity 仍然能够提供出色的训练效率，并且不受它们有限带宽的束缚。

**易用性。** 使用 ZeRO-Infinity，数据科学家不再需要像 3D 并行那样将模型适配到多种并行形式。这得益于上文提到的 ZeRO-Infinity 中 memory-centric tiling，它旨在降低大型单个层的 GPU 内存需求，否则这些层需要模型并行（张量切分）才能放入 GPU 内存。此外，即使扩展到万亿参数规模，ZeRO-Infinity 也通过一种受易用性启发的实现消除了手动模型代码重构的需要，该实现自动完成训练任意模型架构所需的所有通信和数据划分。

本文的主要贡献如下：

- 面向大模型训练的内存和性能表征，描述了大模型训练中不同组件的内存需求（第 3 节）以及为了高效训练所需的带宽需求（第 4 节）。
- ZeRO-Infinity（第 5、6、7 节）：一种新的 DL 训练系统技术，包含五项创新技术，用于满足内存和带宽需求，从而提供前所未有、可访问且易用的模型规模，同时实现出色的训练效率：i）infinity offload engine，通过同时利用 GPU、CPU 和 NVMe 内存以及 GPU 和 CPU 计算来充分利用现代集群上的异构架构；ii）memory-centric tiling，在不需要模型并行的情况下处理巨大算子；iii）bandwidth-centric partitioning，利用所有并行设备上的聚合内存带宽；iv）overlap-centric design，重叠计算和通信；v）ease-inspired implementation，避免模型代码重构。
- 对 ZeRO-Infinity 的全面评估，展示了：i）前所未有的规模，在 32 个 NVIDIA DGX-2 节点（512 块 V100 GPU）上运行 32 万亿参数；ii）出色的训练效率，在同一硬件上实现超过 25 petaflops 的吞吐量；iii）万亿参数模型的超线性可扩展性；iv）可访问性和易用性：无需任何模型并行或模型代码重构，即可在单个 DGX-2 节点上微调高达万亿参数的模型；v）ZeRO-Infinity 中不同技术对模型规模和效率的影响（第 8 节）。
- 对 ZeRO-Infinity 及其对未来硬件系统设计潜在影响的讨论（第 9 节）。
- 在 DeepSpeed[^2] 中提供 ZeRO-Infinity 的开源实现。DeepSpeed 是一个用于让分布式训练变得简单、高效且有效的深度学习优化库，已经被 DL 社区广泛采用。

## 2 背景与相关工作

**数据并行、模型并行、流水线并行和 3D 并行。** 并行化是大规模训练大模型的重要策略。对于一个能够放入设备内存进行训练的模型，可以使用数据并行（DP）将训练扩展到多个设备。当模型无法放入设备内存时，模型并行[^3]（MP）[7, 17, 18] 和流水线并行（PP）[7-9] 可以分别沿垂直方向和水平方向在进程之间切分模型。==3D 并行 [14, 15] 结合了数据并行、模型并行和流水线并行==，以发挥各自优点，使其能够高效扩展到万亿参数规模。虽然 3D 并行可以非常高效，但它需要：i）大量模型代码重构，以将模型拆分为模型并行和流水线并行组件；ii）复杂依赖图的模型难以表示为负载均衡的流水线阶段；iii）模型大小受到总可用 GPU 内存的限制。关于 DL 中并行性的全面综述，读者可参考 Ben-Nun 和 Hoefler [19]。

**ZeRO：零冗余优化器。** ZeRO [11] 通过在数据并行进程之间==划分三类模型状态（即优化器状态、梯度和参数）==而不是复制它们，消除了数据并行进程之间的内存冗余。通过这样做，它在保留经典数据并行的计算粒度和通信效率的同时，提高了内存效率。ZeRO 有三个阶段，对应三类模型状态：第一阶段（ZeRO-1）只划分优化器状态；第二阶段（ZeRO-2）划分优化器状态和梯度；最终阶段（ZeRO-3）划分全部三类模型状态。在 ZeRO-3 中，模型中每一层的参数由唯一的数据并行进程拥有。训练期间，ZeRO-3 通过从拥有者进程发起广播通信集合操作，确保算子的前向或反向传播所需参数在执行前刚好可用。算子执行后，ZeRO-3 也会移除参数，因为在该算子的下一次前向或反向传播之前不再需要这些参数。此外，在训练的参数更新阶段，ZeRO-3 确保每个数据并行进程只更新其拥有参数对应的优化器状态。因此，除了当前计算所需的参数之外，ZeRO-3 能够在整个训练过程中保持所有模型状态都处于划分状态。

**异构训练方法。** 在多种基于 CPU 内存的异构训练方法 [20-26] 中，ZeRO-Offload [12] 是多 GPU 大模型训练的最新最先进方法。ZeRO-Offload 建立在 ZeRO-2 之上，并将梯度和优化器状态存储在 CPU 内存中。当没有足够的 GPU 设备来存储优化器状态和梯度时，ZeRO-Offload 利用 CPU 内存。然而，它仍然要求参数存储在 GPU 内存中并在所有设备上复制。因此，==ZeRO-Offload 的模型规模受限于单个 GPU 设备内存能够容纳的参数总数。由于数据划分不够理想并且 PCIe 带宽有限，ZeRO-Offload 还需要较大的批量大小才能保持高效。ZeRO-Infinity 解决了 ZeRO-Offload 的这些限制。==就基于 NVMe 的方法而言，Zhao 等人 [27] 使用基于分层参数服务器的设计，将稀疏参数卸载到 SSD，以构建超大规模 DL 广告系统。相比之下，ZeRO-Infinity 被设计为一个通用 DL 系统，用于训练巨大的稠密模型。

**减少激活内存。** 激活是在前向传播期间产生的中间结果，需要保留以便在反向传播期间计算梯度。许多工作专注于通过压缩 [28]、激活检查点 [29, 30] 或活跃性分析 [31] 来减少激活所需的内存。ZeRO-Infinity 与激活检查点配合使用，以减少激活内存。

**Adam 优化器和混合精度训练。** 自适应优化方法 [32-35] 对于有效训练大模型并达到最先进性能和准确度至关重要。与 SGD 相比，这类方法为每个模型参数和梯度维护细粒度的一阶和二阶统计信息，代价是显著的内存占用。Adam [33] 是大模型训练中最常用的优化器。

大模型训练通常采用混合精度，其中前向和反向传播使用 FP16，参数更新使用 FP32 [36]。这利用了现代 GPU 上张量核心单元带来的性能加速 [37]。

## 3 内存需求

本节表征 DL 训练的内存需求。虽然我们的方法是通用的，但由于所有超过十亿参数的最先进模型都遵循 Transformer [38] 架构，因此我们将具体分析聚焦在基于 Transformer 的架构上。我们的分析假设使用 Adam 优化器进行混合精度训练，因为这是训练基于 Transformer 模型的事实标准方案。

训练所需内存可以分为两个组成部分：i）模型状态，包括优化器状态、梯度和模型参数；ii）残余状态，主要指激活内存。为了研究异构资源上的训练，我们还表征 GPU 工作内存，即假设模型状态和残余状态能够成功从 GPU 内存卸载时，为支持训练而必须在 GPU 上可用的最小内存量。

**模型状态的内存。** 模型状态由优化器状态、梯度和参数组成。对于使用 Adam 优化器的混合精度训练，参数和梯度以 FP16 存储，而优化器状态由 FP32 动量、方差、参数和梯度组成。总体而言，每个参数需要 20 字节内存。基于 Transformer 的模型中参数总数主要取决于隐藏维度（hd）和 Transformer 层数（nl）。Transformer 块中几乎所有参数都来自每个块内的四个线性层，其大小分别为：(hd, 3hd)、(hd, hd)、(hd, 4hd) 和 (4hd, hd)。因此，基于 Transformer 的模型的总参数量可近似为：$12 \times n_l \times h_d^2$。存储模型状态总共需要如下字节数: $240 \times n_l \times h_d^2$。图 2a 第 5 列显示了通过改变隐藏维度和层数构建的 GPT-3 类 Transformer 模型（从 1000 亿到 100 万亿参数）存储模型状态所需的内存。为了提供内存需求的背景，图 2b 第 3 列显示了单个 NVIDIA V100 DGX-2 机器以及 DGX-2 SuperPOD 集群上可用的聚合 GPU 内存。注意，仅为了容纳一个 1000 亿参数模型的模型状态，就需要 64 块 GPU。容纳一个万亿参数模型需要超过 512 块 GPU，而 10 万亿参数模型则超出了即使是 1536 块 GPU 的大型集群的范围。

**残余状态的内存。** 残余状态主要由激活内存组成，它取决于模型架构、批量大小（bsz）和序列长度（seq），并且可能非常大。积极的一面是，通过激活检查点 [29] 可以显著减少激活所需内存，其代价是增加 0.33 倍的额外重计算。Turing-NLG 17.2B 和 GPT-3 175B 等大模型都使用激活检查点进行训练。存储激活检查点所需的内存估计为：$2 \times bsz \times seq \times h_d \times n_l / ci$其中 ci 是两个激活检查点之间的 Transformer 块数，而 $bsz × seq × h_d$ 是每个 Transformer 块输入的大小。图 2a 第 7 列显示了在批量大小为 32、序列长度为 1024 且假设每个 Transformer 块存储一个激活的情况下，存储激活检查点所需的内存。许多现代 GPU 集群每个节点有 8-16 块 GPU，因此我们选择每块 GPU 批量大小为 2-4，即每个节点批量大小为 32，作为每个节点内激活的保守估计。虽然得到的激活检查点比完整激活集合（第 6 列）小几个数量级，但当超过万亿参数时，在所考虑的批量大小和序列长度下，它们仍然大到无法放入 GPU 内存。

**模型状态工作内存（MSWM）。** 模型状态工作内存是指在所有模型状态已从 GPU 内存卸载到 CPU 或 NVMe 后，为了在模型中最大的单个算子上执行前向或反向传播而所需的最小 GPU 内存。这近似等于该算子中参数和梯度的大小，因为至少必须有足够内存来容纳反向传播所需的参数及其梯度。对于基于 Transformer 的模型，最大算子是一个将隐藏状态从 hd 变换为 4hd 的线性层。该线性层参数和梯度的大小（字节）为：$4 × hd × 4hd$。注意，MSWM（图 2a 第 8 列）在超过 1000 亿参数后显著增长，需要多个 GB 的连续内存，这可能由于没有足够连续内存满足这些需求而导致训练时内存耗尽。3D 并行等最先进方法通过模型并行将单个算子拆分到多个 GPU 上来解决这一问题。在第 5.1.3 节中，我们讨论一种新的方法，在不需要模型并行的情况下解决这些巨大的模型状态工作内存需求。

**激活工作内存（AWM）。** 激活工作内存是在反向传播中，在执行真正的反向传播之前重新计算激活所需的内存。它是两个连续激活检查点之间的激活大小。例如，如果每个 Transformer 块创建一个激活检查点，那么该内存由每个 Transformer 块的总激活大小给出，字节数近似为：
$bsz \times seq \times ci \times (16 \times h_d + 2 \times attn\_heads \times seq)$
图 2a 第 8 列显示，即使 ci = 1，当参数超过 10 万亿时 AWM 也会变大。与仅由单个参数和梯度组成的 MSWM 不同，AWM 由几十个激活组成；只要总 AWM 能够放入 GPU 内存，就不会因为缺少连续内存而导致内存问题。

## 4 带宽需求

卸载到 CPU 和 NVMe 内存的一个关键问题是它们有限的带宽是否会损害训练效率。本节表征带宽对训练效率的影响。

我们从定义一个效率指标开始。假设工作负载执行时没有任何计算与通信重叠，则可以使用峰值计算吞吐量（peaktp）、数据移动带宽（bw）及其算术强度（ait）来估计训练效率。

算术强度（AIT）是工作负载总计算量与计算所需数据量之间的比值。它描述每次数据移动对应的计算量。更高的 AIT 意味着对数据移动带宽的要求更低，因为每加载一份数据，加速器可以执行更多计算。可以推导出效率测度为：
$$  
compute\_time = \frac{total\_computation}{peak_{tp}}  
$$
$$  
ait = \frac{total\_computation}{total\_data\_movement}  
$$
$$  
communication\_time  
=  
\frac{total\_data\_movement}{bw}  
=  
\frac{total\_computation}{ait \times bw}  
$$
$$  
efficiency  
=  
\frac{compute\_time}{compute\_time + communication\_time}  
$$
效率可以写成peaktp，bw和ait的函数：$$  
efficiency  
=  
\frac{ait \times bw}{ait \times bw + peak_{tp}}           (6)
$$
我们将使用这个简单的效率公式来表征训练巨大模型所需的数据移动带宽。但在此之前，我们首先量化 DL 训练工作负载中的 ait。

### 4.1 量化 DL 训练中的 AIT

模型状态和激活检查点可以具有不同的 ait。我们可以通过先识别 DL 训练每次迭代中的总计算量，然后识别每种模型状态和激活的数据移动量来量化它们。

**每次迭代的总计算量。** 每次迭代的总计算量由 Transformer 中线性层的计算主导。对于前向传播，它可以近似表示为参数数量、序列长度和批量大小的函数，即 2 × bsz × seq × params。反向传播的成本约为前向传播的两倍。此外，激活检查点在反向传播期间需要额外一次前向计算作为重计算。因此，每次迭代的总计算量为：
%%对于每一个token进行乘+加两次运算，反向传播需要对权重和激活都进行求偏导，对权重求偏导是为了更新权重，对激活求偏导是为了传递给上一层进行计算%%
$computation\_per\_iter = 2 × 4 × bsz × seq × parameters = 2 × 4 × 12 × bsz × seq × nl × hd²$

**相对于参数和梯度的 AIT。** 在前向和反向传播期间，模型参数至少必须从源位置加载到 GPU 寄存器两次：i）前向期间；ii）实际反向期间，因此产生 2 × parameters 的数据移动。在存在激活检查点时，参数可能还要在反向传播中的重计算期间再加载一次，增加 1 × parameters。此外，梯度必须至少从 GPU 寄存器存储到最终位置一次，进一步增加 1 × parameters 的数据移动。

因此，假设参数和梯度存储在同一最终位置，前向和反向传播期间的总数据移动量将为 4 × parameters，即以字节计为 2 × 4 × parameters。每次迭代的总计算量如第 4.1 节所述。因此，相对于参数和梯度的 ait 为：$seq × bsz$

**相对于优化器状态的 AIT。** 在优化器步骤中，优化器状态至少必须读取一次，并且优化器状态至少必须写入一次。因此，总数据移动量为 2 × optimizer_states，约为 2 × 16 × parameters 字节。每次迭代的总计算量如第 4.1 节所述。因此，完整训练迭代期间相对于优化器状态的 ait 为：
$seq × bsz / 4$

**相对于激活检查点的 AIT。** 在前向传播期间，激活检查点必须保存到最终位置，并且必须在反向传播期间取回。因此，相对于激活检查点的总数据移动量（以字节计）为 $2 × total\_activation\_checkpoints\_in\_bytes$，根据公式 (3) 可表示为 $4 × nl/ci × hd × seq × bsz$。每次迭代的总计算量如第 4.1 节所述。因此，相对于激活检查点的 ait 为：
$24 × hd × ci$

由于 AIT 的差异，模型状态和激活检查点为了达到良好效率具有非常不同的带宽需求。前者只取决于批量大小和序列长度，而后者只取决于激活检查点频率和模型的隐藏维度大小。

### 5.1 面向前所未有规模的设计

现代 GPU 集群在内存存储方面高度异构。除了 GPU 内存之外，它们还具有 CPU 内存以及巨大的 NVMe 存储，后者比 GPU 内存大 50 倍以上，并且接近 CPU 内存的 20 倍（见图 2b）。

我们开发了 ZeRO-Infinity，这是一个用于 DL 训练的并行系统，它能够通过利用现代 GPU 集群中的这些异构内存系统来超越 GPU 内存墙。图 1 比较了 3D 并行和 ZeRO-Infinity 所达到的最大模型大小。ZeRO-Infinity 支持每个 NVIDIA V100 DGX-2 节点一万亿参数，相比 3D 并行提升 50 倍。

#### 5.1.1 用于模型状态的 infinity offload engine

ZeRO-Infinity 建立在 ZeRO-3 [11] 之上，==ZeRO-3 通过划分所有模型状态来消除内存冗余==，如第 2 节所述。不同于任何现有 ZeRO 系列技术，ZeRO-Infinity 设计了一个强大的卸载机制，称为 ==infinity offload engine==，它能够根据内存需求将全部划分后的模型状态卸载到 CPU 或 NVMe 内存，也可以将它们保留在 GPU 上。从图 2a 和图 2b 可见，即使 100 万亿参数模型所需的模型状态也可以放入一个具有 96 个节点（1536 块 GPU）的 DGX-2 集群的聚合 NVMe 内存中。因此，infinity offload engine 使 ZeRO-Infinity 能够容纳具有数百万亿参数的模型状态。更多细节见第 6 节。

#### 5.1.2 激活的 CPU 卸载

除了模型状态，在必要时，ZeRO-Infinity 还可以将激活内存卸载到 CPU 内存。注意，10 万亿参数模型所需的激活检查点（0.76 TB）可以轻松放入 DGX-2 系统可用的 1.5 TB CPU 内存中，而 100 万亿参数模型所需的 3 TB 激活检查点在下一代硬件的 CPU 内存能力范围内。因此，通过将激活检查点卸载到 CPU 内存，ZeRO-Infinity 能够容纳具有数百万亿参数的模型的激活检查点。

#### 5.1.3 用于工作内存的 memory-centric tiling

为了降低大模型 DL 训练的工作内存需求，ZeRO-Infinity 引入了一种新的技术，称为 memory-centric tiling。它利用 ZeRO-3 的数据获取和释放模式，通过将大型算子拆分为可以顺序执行的小块来降低工作内存需求。

例如，为了降低大型线性算子的工作内存，ZeRO-Infinity 将该算子表示为由原始算子参数块构成的、在数学上等价的一系列较小线性算子，并顺序执行它们。当与 ZeRO-3 结合时，每个块的参数和梯度可以一次获取和释放一个，从而按块数比例降低工作内存。因此，ZeRO-Infinity 可以支持任意大小的算子，而不依赖模型并行将其放入有限 GPU 内存中。

### 5.2 面向出色训练效率的设计

将所有模型状态和激活卸载到 CPU 或 NVMe，只有在 ZeRO-Infinity 即使存在卸载也能实现高效率时才是实用的。事实上，这极具挑战性，因为 CPU 内存带宽比 GPU 内存带宽慢一个数量级，而 NVMe 带宽又比 CPU 内存带宽再慢一个数量级。此外，从 GPU 读写这些内存甚至更慢（见图 2b）。

根据第 4 节的分析，在 DGX-2 这样的系统上，为了使 DL 训练高效，相对于参数和梯度、优化器状态以及激活检查点，带宽必须分别大于 70 GB/s、1.5 TB/s 和 1-4 GB/s。下面讨论 ZeRO-Infinity 如何达到必要带宽以实现出色效率。

#### 5.2.1 相对于参数和梯度的效率

参数和梯度的数据移动带宽必须超过 70 GB/s，接近 DGX-2 集群上的 GPU-GPU 带宽 [40]。因此，只要通信可以重叠，像 ZeRO-3 [11] 这样的 DL 并行训练方案，即在前向或反向传播使用参数之前由拥有者 GPU 将参数广播给其他 GPU，就能够高效运行。

相反，从单块 GPU 到 CPU 内存或 NVMe（见图 2b）或者反向的 PCIe 带宽只有约 12 GB/s，根本不足以支持大规模异构训练[^6]。因此，现有异构方案（如 ZeRO-Offload）中，参数必须先从 CPU 移动到拥有者 GPU，然后再广播；在有限带宽下，为了达到足够高的 ait 并保持高效，需要每块 GPU 有显著较大的批量大小。这带来两个问题：i）对于巨大模型，激活内存会变得过大，甚至无法放入 CPU 内存；ii）当扩展到数百或数千块 GPU 时，有效批量大小会变得过大，不利于有效收敛。

ZeRO-Infinity 通过两种方式解决这些挑战：i）bandwidth-centric partitioning：一种新的数据映射和并行数据检索策略，用于卸载后的参数和梯度，使 ZeRO-Infinity 能够实现几乎无限的异构内存带宽（详见第 6.1 节）；ii）overlap-centric design，使 ZeRO-Infinity 不仅可以将 GPU-GPU 通信与计算重叠，还可以通过 PCIe 将 NVMe-CPU 和 CPU-GPU 通信与计算重叠（详见第 5.1.3 节）。

#### 5.2.2 相对于优化器状态的效率

不同于在前向和反向传播期间顺序消费和产生的参数与梯度，优化器状态可以并行、一次性更新。ZeRO-3 和 ZeRO-Offload 都利用了这一特性，分别在 GPU 和 CPU 内存中跨所有可用 GPU 和 CPU 并行存储和更新优化器状态。因此，随着 GPU 或 CPU 数量增加，聚合 GPU 或 CPU 内存带宽可以远高于所需的 1.5 TB/s。

由于 ZeRO-Infinity 建立在 ZeRO-3 之上，在将优化器状态卸载到 CPU 内存时，它也可以利用聚合 GPU 和 CPU 内存带宽以及聚合 CPU 计算来执行优化器步骤。然而，在 NVMe 卸载时，需要将数据从 NVMe 分块带到 CPU 内存并再写回，每块大小必须能放入 CPU 内存，以便逐块执行优化器步骤。因此，优化器步骤受到 NVMe-CPU 内存带宽限制：虽然 ZeRO-Infinity 可以跨多个节点实现聚合 NVMe 带宽，但为了用尽可能少的节点、尽可能小的批量大小支撑超过 1.5 TB/s 的必要带宽，单节点达到接近峰值 NVMe 带宽至关重要。此外，在 NVMe 与 CPU 内存之间、或者 CPU 内存与 GPU 内存之间来回移动数据的过程可能造成 CPU 和 GPU 内存碎片，即使仍有大量可用内存也会导致内存不足。

infinity offload engine 不仅可以实现接近峰值的 NVMe 带宽，还允许 ZeRO-Infinity 同时重叠 NVMe 到 CPU 的读取、CPU 到 NVMe 的写入以及优化器步骤的 CPU 计算，从而使 ZeRO-Infinity 在少量 GPU 上使用适中批量大小、或在大量 GPU 上使用小批量大小时仍然保持高效。同时，它通过谨慎复用数据移动临时缓冲区来最小化内存碎片。我们在第 6 节详细讨论 infinity offload engine 中的优化。

#### 5.2.3 相对于激活的效率

在 DGX-2 节点上，每块 GPU 可以通过 PCIe 并行以约 3 GB/s 的速度读写 CPU 内存，这使得激活检查点可以卸载到 CPU 内存，并且在隐藏大小大于等于 8K 时仍保持超过 80% 的效率。为了在较小隐藏大小下也实现高效率，ZeRO-Infinity 可以降低激活检查点频率，并有效地将激活检查点在 CPU 内存与 GPU 之间的通信与 GPU 上的前向和反向计算重叠。

### 5.3 面向易用性的设计

使用 ZeRO-Infinity，数据科学家不再需要像 3D 并行那样将模型适配到多种并行形式。这得益于第 5.1.3 节讨论的 ZeRO-Infinity 中的 memory-centric tiling，它旨在降低大型单个层的 GPU 内存需求，否则这些层需要模型并行（张量切分）才能放入 GPU 内存。

此外，ZeRO-Infinity 以一种无需手动模型代码重构的方式在 PyTorch 中实现，即使扩展到万亿参数也如此。这通过具有两个自动化功能的易用性启发式实现来完成：

i）自动数据移动，在训练期间参数需要使用之前和使用之后，自动收集和划分参数。ZeRO-Infinity 通过向 PyTorch 子模块注入：i）前向/反向前钩子，触发 allgather 集合操作以在前向/反向传播之前收集所需参数；ii）前向/反向后钩子，触发参数/梯度划分，并可选地将其卸载到 CPU 或 NVMe（详见第 7.1 节）。

## 6 效率优化

本节深入讨论第 5 节引入的优化，这些优化使 ZeRO-Infinity 能够实现出色效率。

### 6.1 Bandwidth-Centric Partitioning

ZeRO-Infinity 实现了一种新的数据映射和检索策略，以解决 NVMe 和 CPU 内存带宽限制。与 ZeRO [11] 和 ZeRO-Offload [12] 不同，后两者中每层参数由单个数据并行进程拥有，并在需要时广播给其他进程；ZeRO-Infinity 将单个参数划分到所有数据并行进程上，并在参数需要访问时使用 allgather 而不是 broadcast。注意，如果数据位于 GPU 上，就数据移动量而言，broadcast 和 allgather 通信集合操作具有相同的通信成本。因此，这对纯 GPU 训练没有区别。然而，当数据位于 NVMe 或 CPU 中时，这会带来根本改变。

在基于 broadcast 的方法中，由于每个参数完全由一个数据并行进程拥有，所以在广播发生之前，参数必须先通过 PCIe 从其源位置传输到 GPU 内存。注意，在这个过程中只有单条 PCIe 链路处于活动状态，而连接其他所有 GPU 的 PCIe 链路都空闲。相反，在 ZeRO-Infinity 的参数划分与 allgather 方法中，所有 PCIe 链路并行处于活动状态，每条链路带入参数的 1/dp 部分，其中 dp 是数据并行度。因此，NVMe 或 CPU 到 GPU 的有效通信带宽随着 dp 度线性增加。

例如，在基于 broadcast 的方法中，即使在 DGX-2 机器上使用 16 路数据并行，CPU/NVMe 到 GPU 的带宽在 PCIe Gen 3 下仍保持约 12 GB/s。然而，使用基于 allgather 的方法，可达有效带宽分别增加到约 48/25 GB/s（每块 GPU 3.0/1.6 GB/s）（见图 2b），仅受每个 DGX-2 节点的最大聚合 PCIe 带宽和最大 NVMe 带宽限制。从这里开始，带宽会随着更多节点线性增长。当以超大规模训练巨大模型时，ZeRO-Infinity 因而可以为训练保持高效提供显著超过必要水平的异构内存带宽（几乎无限）。例如，在 64 个 DGX-2 节点上，ZeRO-Infinity 可以访问超过 3 TB/s 的 CPU 内存带宽和超过 1.5 TB/s 的 NVMe 带宽。

### 6.2 Overlap-Centric Design

虽然 ZeRO-Infinity 可以在多节点设置中利用足够的异构内存带宽，但在单 GPU 或单节点设置中，带宽仍可能成为瓶颈。即使是 GPU-GPU allgather 通信，在小批量大小运行时也会对效率产生很大影响（图 3）。此外，访问 NVMe 内存需要三步过程：i）从 NVMe 读取数据到 CPU 内存（nc-transfer）；ii）将数据从 CPU 内存复制到 GPU 内存（cg-transfer）；iii）执行 allgather 以在所有 GPU 上构造完整参数（gg-transfer）。这些数据移动的顺序性质意味着，如果天真地执行，总通信时间将是三种数据移动成本之和，即使每个阶段的数据移动带宽单独都足够，也会导致低效率。

为了解决这些问题，ZeRO-Infinity 配备了一个重叠引擎，它不仅将 GPU-GPU 通信与 GPU 计算重叠，还同时重叠 NVMe 到 CPU 和 CPU 到 GPU 的通信。该重叠引擎包含两个组件：i）动态预取器，用于重叠在前向或反向传播中消费参数之前重构参数所需的数据移动；ii）通信与卸载重叠机制，用于在反向计算并行执行时执行梯度所需的数据移动。

ZeRO-Infinity 中的动态预取器会即时跟踪前向和反向计算，为每次迭代构建算子序列的内部映射。在每次迭代中，预取器跟踪它在算子序列中的位置，并预取未来算子所需的参数。预取器了解三步通信过程，因此可以将某个参数的 nc-transfer 与其他参数的 cg-transfer 和 gg-transfer 重叠。例如，在执行第 i 个算子之前，预取器可以分别对第 i+3、i+2 和 i+1 个算子所需的参数发起 nc、cg 和 gg-transfer。注意，所有这些数据移动都可以与第 i 个算子的执行并行发生。此外，在动态工作流情况下，ZeRO-Infinity 可以更新算子序列映射，从而即使前向和反向传播跨迭代发生变化，也能进行适当预取。

类似地，在反向传播中，ZeRO-Infinity 可以将第 (i+1) 个算子的参数梯度的 reduce-scatter 与第 i 个算子的计算重叠，同时将第 (i+2) 个算子的梯度 reduce-scatter 后得到的划分梯度传输到 CPU 或 NVMe。

借助这种强大的 overlap-centric design，即使在使用少量 GPU 和每块 GPU 小批量大小训练时，ZeRO-Infinity 也能隐藏大量数据移动。

### 6.3 Infinity Offload Engine

infinity offload engine 由两个主要组件组成：

**DeepNVMe。** DeepNVMe 是 infinity offload engine 中一个强大的 C++ NVMe 读写库，支持批量读写请求的异步完成，以及用于刷新正在进行的读写的显式同步请求。异步支持允许 ZeRO-Infinity 将这些请求与 GPU/GPU 或 GPU/CPU 通信或计算重叠。

最重要的是，DeepNVMe 能够在 NVMe 存储设备上实现接近峰值的顺序读写带宽。它通过多项优化达到这种高性能，包括积极并行化 I/O 请求（无论来自单个用户线程还是多个用户线程）、智能工作调度、避免数据复制以及内存固定。

**固定内存管理层。** 为了确保从 NVMe/CPU 存储进行高性能张量读取（或写入到 NVMe/CPU 存储），源（或目标）张量必须驻留在固定内存缓冲区中。然而，固定内存缓冲区是稀缺系统资源，单个进程过度订阅可能降低整体系统性能或导致系统不稳定。该层通过复用少量（数十 GB）固定内存，来将整个模型状态（最高可达数十 TB）卸载到 CPU 或 NVMe。内存缓冲区复用避免了 CPU 和 GPU 内存碎片。该层还为 PyTorch 张量提供固定内存数据，允许对张量进行原地计算，从而之后无需进一步复制即可写入 NVMe，以提高带宽。

## 7 受易用性启发的实现

ZeRO-Infinity 构建在 PyTorch 之上，并设计为无需任何模型代码重构即可使用，类似 PyTorch 中的标准数据并行训练。本节详细说明实现这样一个系统时面临的一些挑战。

### 7.1 自动化数据移动

ZeRO-Infinity 必须协调组成模型参数、梯度和优化器状态的张量移动。当张量未被主动使用时，它保持在 worker 之间被划分，并且可能被卸载到 CPU 或 NVMe 内存。系统必须确保这些张量在使用前及时驻留到 GPU 内存中，之后再重新划分。

PyTorch 模型表示为模块层次结构，这些模块代表神经网络的层。例如，Transformer 架构 [38] 包含自注意力和前馈网络等子模块。自注意力子模块又进一步由线性变换和其他子模块组成。

ZeRO-Infinity 递归地将钩子注入模型子模块，以自动化所需的数据移动。在子模块前向传播开始时，这些钩子确保该子模块的参数可用于计算；否则，它会执行适当的 allgather 集合操作，并阻塞直到参数可用。第 6.2 节详细说明的 overlap-centric design 对于最小化参数通信导致的停顿至关重要。在子模块前向传播结束时，我们再次划分参数，并可选地卸载它们。反向传播以类似方式处理。

#### 7.1.1 外部参数的自动注册

理想情况下，子模块的参数和梯度只在其自身前向和反向传播中访问，这使得如上文所述识别和自动化数据移动很直接。然而，一些模型架构是例外，其中在某个子模块中定义和分配的参数会在另一个子模块的前向和反向传播中使用。例如，GPT [41] 等语言模型在网络的开头和结尾共享嵌入层权重，以分别将词映射为向量以及反向映射。我们将跨模块边界使用的参数称为外部参数。在存在外部参数时，很难知道在某个子模块的前向和反向传播开始时应收集哪些参数。

一种解决方法是将外部参数注册到 ZeRO-Infinity，使它们在访问它们的子模块的前向和反向传播中被收集。注册后，外部参数像所有其他参数一样处理，并会被纳入第 6.2 节所述的预取系统。我们提供了用于手动注册外部参数的 API。

为了改善用户体验，我们还提供机制来检测这些场景并自动注册外部参数，使用户不必做任何代码更改：

**拦截被划分参数访问。** PyTorch 模块将它们的张量参数存储在哈希表中。在初始化时，我们用一个子类化类型替换该哈希表，以覆盖张量访问。当访问一个被划分的参数时，我们对该参数执行阻塞 allgather，将其注册为外部参数，然后返回收集后的参数。

**激活内省。** 子模块可能从其前向传播中返回一个参数，供另一个子模块的前向和反向传播使用。例如，Megatron-LM 从线性层的前向传播中返回偏置向量，并由父 Transformer 层模块消费。我们检查每个子模块前向传播返回的激活输出，以寻找被划分参数。如果发现一个，我们就收集并注册它为外部参数。

### 7.2 初始化期间的自动模型划分

如果模型很大，则可能无法使用传统数据并行方法完整初始化模型，即在每个数据并行进程上复制模型，然后再为 ZeRO-Infinity 对其进行划分。例如，一个 5000 亿参数模型在半精度下将占用 1 TB 内存，因此一个每节点 8 块 GPU 的系统仅为了初始数据并行分配步骤，就需要 8 TB 的聚合 CPU 或 GPU 内存。这超出了单个节点可用的 GPU 或 CPU 内存。

为了解决这一限制，模型每一层对应的参数必须在初始化时划分，而不是在整个模型初始化之后划分。为此，我们提供了一个 Python ZeRO-Infinity 上下文，它装饰 torch.nn.Module 的 __init__ 方法，使得每个模块/子模块下分配的参数在初始化后立即在数据并行进程组中划分。

因此，只有单个子模块在划分前会被完整初始化，而完整模型从不会在所有数据并行进程上复制。在上述示例中，5000 亿参数模型因此可以在初始化期间被完全划分，无论数据并行进程总数是多少，只需要 1 TB 聚合 CPU 内存。

### 8.3 超线性可扩展性

图 5b 显示，在训练 1T 模型时，ZeRO-Infinity 从 4 个节点（64 块 GPU）到 32 个节点（512 块 GPU）实现了超线性可扩展性。这是一个弱扩展结果，即我们保持每节点批量大小恒定，并随着节点数增加而增加总批量大小。ZeRO-Infinity 通过有效利用聚合 PCIe 和 NVMe 带宽的线性增长来加速参数和优化器状态卸载，并利用额外节点的 CPU 计算进行参数更新，从而超过完美线性扩展。此外，ZeRO-Infinity 仅使用 4 个节点时就已经达到超过 2.8 petaflops（44 Tflops/GPU），说明即使在适中规模下，聚合 NVMe 带宽也足以实现良好效率。

### 8.4 普及大模型训练

图 5c 显示了 ZeRO-Infinity 在单个节点（16 块 GPU）上无需任何模型并行训练 10B 到 1T 模型的性能。对于最高 1000 亿参数的模型，ZeRO-Infinity 达到超过 40 TFlops/GPU 的出色性能，使得仅用一个 DGX-2 机器微调 GPT-3 等模型成为可能。相比之下，3D 并行无法扩展到超过 200 亿参数的模型。

这些结果展示了 ZeRO-Infinity 的两个方面：i）可访问性：可以在单个 NVIDIA DGX-2 节点上微调最高万亿参数的大模型，使无法访问大型 GPU 集群的用户也能受益；ii）易用性：这种规模的模型可以使用 ZeRO-Infinity 训练，而无需组合模型并行或流水线并行，也不需要模型代码重构，使数据科学家能够轻松扩展模型。

## 9 结论与未来影响
![[.assets/Pasted image 20260602185705.png]]
[表 3：当加速器设备的可达计算能力比 NVIDIA V100 GPU 高 10 倍和 100 倍时，ZeRO-Infinity 在 512 个加速器设备集群上保持高效所需的带宽（bw）。表格占位。]

在本文中，我们提出了 ZeRO-Infinity，这是一种新的异构系统技术，它利用 GPU、CPU 和 NVMe 内存，使前所未有且易访问、易使用的模型规模成为可能，同时实现出色效率。它改变了我们思考大模型训练内存的范式。DL 训练不再必须全部适配到 HBM2 这种超高速但昂贵且有限的内存中。ZeRO-Infinity 展示了，通过在多个设备上并行利用廉价、较慢但容量巨大的 CPU 或 NVMe 内存，可以获得高效训练所需的聚合带宽，从而突破当前一代 GPU 集群上的 GPU 内存墙。

展望未来，GPU 和其他加速器将变得更强大，高效训练所需的聚合带宽也会增加。表 3 显示，即使加速器计算能力相比 NVIDIA V100 GPU 提高 10 倍，在一个包含 512 个加速器的集群上，ZeRO-Infinity 为保持高效也只需要每个加速器与慢速内存之间有 30 GB/s 的带宽。事实上，用今天的技术已经可以通过 NVLink [43] 将加速器连接到慢速内存来实现这一点。例如，2018 年上线的 Summit 超级计算机 [44] 将 NVIDIA V100 GPU 与 CPU 内存以每块 GPU 40 GB/s 的带宽连接起来。

显然，借助 ZeRO-Infinity，加速器设备内存不再需要成为未来 DL 模型规模的瓶颈。相反，只要能够通过足够带宽访问大量慢速内存，大模型训练就可以继续扩展。这也表明，未来的硬件系统可以重新思考高带宽设备内存与大容量慢速内存之间的平衡；与其不断扩大昂贵的设备内存容量，不如提供更强的异构内存访问路径、更高的聚合慢速内存带宽以及更高效的异步数据移动能力。ZeRO-Infinity 为这种系统设计方向提供了软件和系统层面的证据。
