### VHDL 有限状态机

默认的有限状态机处理会使 `PRGRM_FSM` 产生 `ELAB-1094`，并使后续 DFT 检查出现黑盒提示。读取 RTL 前加入下列设置后，Lab 4A、Lab 5、Lab 6 和 Lab 7 可以正常编译。

```tcl
set_app_var hdlin_always_fsm_complete false
```

**问题含义**：旧 VHDL 中 `PRGRM_FSM` 的状态编码并不满足当前工具默认的完整状态机假定。默认设置会令部分状态不可用，随后 DFT 检查把相关逻辑视为不完整模型。

**修复范围**：该设置只在读 RTL 前使用，不能代替设计级状态机审查。对于新项目，仍应检查状态定义、复位状态、默认分支和不可达状态。

### 多扫描时钟定义

旧脚本把三个时钟放在一个 `-port` 参数中。当前版本要求每条 `set_dft_signal` 只指定一个端口，因此改为三条命令。

```tcl
set_dft_signal -view existing_dft -type ScanClock -timing {45 55} -port pclk
set_dft_signal -view existing_dft -type ScanClock -timing {45 55} -port sdr_clk
set_dft_signal -view existing_dft -type ScanClock -timing {45 55} -port sys_clk
```

**学习要点**：`-view existing_dft` 描述已经存在于设计中的端口属性；一个命令只声明一个端口，报告更容易定位问题。`{45 55}` 表示在测试波形表中把上升沿放在 45、下降沿放在 55 的时间位置。

### VHDL 总线位端口

当前 VHDL 读取器会以转义形式保存总线位名称。直接写 `Instrn[0]`、`pad[0]` 等文字会导致端口查找失败。脚本改为从端口集合中取得位 0，再传给 DFT 命令。

```tcl
set scan_in_port  [index_collection [get_ports {Instrn*}] 31]
set scan_out_port [index_collection [get_ports {Xecutng_Instrn*}] 31]
set_dft_signal -view spec -port $scan_in_port -type ScanDataIn
set_dft_signal -view spec -port $scan_out_port -type ScanDataOut
```

Lab 8 与 Lab 9 使用同一方式取得 `pad[0]` 至 `pad[5]`、`sd_A[0]` 至 `sd_A[5]`。运行报告已确认扫描端口、hookup pin 和链名正确。

**为什么索引是 31**：`get_ports {Instrn*}` 返回 32 位端口时，顺序从 `Instrn[31]` 到 `Instrn[0]`。`index_collection ... 31` 因而取得位 0。使用前可用以下命令确认顺序：

```tcl
query_objects [get_ports {Instrn*}]
query_objects [index_collection [get_ports {Instrn*}] 31]
```

不要把该数字复制到位宽不同的设计中；应先查看端口集合，再计算位 0 的位置。

### Lab 7 的 AutoFix

`lab7_fixing/scripts/autofix.tcl` 原来只保留空命令。已补充时钟、复位和置位的 AutoFix 设置，并在预览前重建测试协议。

```tcl
set_dft_configuration -fix_set enable -fix_reset enable -fix_clock enable
set_dft_signal -view spec -type TestMode -active_state 1 -port TEST_MODE
```

**为什么要重建协议**：`set_dft_signal -view spec` 改变的是测试规格，不会自动改写已经创建的 test protocol。`remove_test_protocol` 清除旧协议，随后 `create_test_protocol` 依据新规格生成协议；否则预览仍可能使用旧的时钟、复位或 TestData 定义。

### Lab 10 的层次化测试模型

旧实验把 `create_ilm` 作为接口逻辑模型（ILM，interface logic model）的生成命令。当前 DC `V-2023.12-SP3` 不提供该命令，因此采用 `write_test_model` 生成测试模型，并用 `read_test_model` 在顶层读入。该文件只保留端口、测试控制和扫描边界信息，不包含子模块内部的完整门级实现。

```tcl
# 在完成模块扫描插入后生成测试模型
write_test_model -format ddc -output dc_ilms/${design}.ddc

# 顶层读入所有模块的测试模型
read_test_model [glob dc_ilms/*.ddc]
```

> [!important] 覆盖率的适用范围
> 接口测试模型用于检查层次边界的时钟、测试控制和扫描端口。它不含模块内部故障，因此接口模型流程的 7.05% DFTC 估算值及 0.57% TestMAX 值不能代表整芯片故障覆盖率。整芯片的有效 ATPG 结果应使用自顶向下或 bottom-up 导出的完整门级网表。

### Lab 12 的 Adaptive Scan 设置

Adaptive Scan（自适应扫描）在芯片引脚侧使用较少的扫描输入、输出，在芯片内部使用更多较短的扫描链。该实验定义 5 条外部扫描链，并要求至少 5 倍压缩：

```tcl
set_dft_configuration -scan_compression enable
set_scan_compression_configuration -minimum_compression 5
create_port -direction in TM_COMP
set_dft_signal -view spec -type TestMode -port TM_COMP
```

插入后，`Internal_scan` 模式保留 5 条长度为 586、585、585、585、585 的外部链；`ScanCompression_mode` 产生 30 条内部链，其中 16 条长 98、14 条长 97。30 除以 5 为 6，满足最小 5 倍压缩要求。

当前版本在 `insert_dft` 处理压缩结构的末尾会显示三条 `unknown command '_snps_array_peek'`。经单独复跑确认，即使去掉实例名前缀并且不切换测试模式，该信息仍在 `insert_dft` 结束后出现；它来自工具内部 Tcl 调用。扫描网表、两份 SPF、DDC、SCANDEF 均已写出，随后 DRC、SCANDEF 和 TestMAX 检查均成功，因此将其记录为该版本的内部提示，而非脚本错误。

## 按实验学习与操作引导

### Lab 4A：从 RTL 建立最小测试协议

**目标**：理解“读 RTL → 声明 DFT 信号 → 创建协议 → DFT DRC”的最小过程。

**先看什么**：

- RTL 顶层和时钟、复位端口。
- `set_dft_signal` 中的 `ScanClock`、`Reset`、`ScanEnable`、`Constant`。
- `create_test_protocol` 后的 DRC 汇总。

**推荐操作顺序**：

```tcl
set_app_var hdlin_always_fsm_complete false
source .synopsys_dc.setup
source .solutions/unmapped.tcl
create_test_protocol
dft_drc
report_dft_signal
```

**应观察的结果**：报告最终为 0 项违规；顺序单元统计为 260 个有效扫描单元和 1 个非扫描移位寄存器单元。

**学习笔记**：测试协议不是测试向量。它定义测试期间端口如何动作，例如哪个端口提供时钟、复位的有效电平是什么、扫描使能在何种电平有效。ATPG 在此基础上生成 pattern。

**自测问题**：

> [!question] 为什么 `create_test_protocol` 在 `dft_drc` 之前？
> 因为 DFT DRC 需要知道测试时钟、复位和控制端口的定义。没有协议时，工具无法判断测试模式下信号是否可控制和可观察。

> [!question] 1 个非扫描移位寄存器单元是否一定是错误？
> 不一定。自动识别的移位寄存器可以按工具规则不替换为扫描触发器。应查看报告说明和目标测试策略，再决定是否需要强制处理。

### Lab 8：六条顶层扫描链与 lock-up latch

**目标**：把顶层 `pad[0:5]`、`sd_A[0:5]` 固定为链端点，并在多时钟条件下生成平衡的扫描链。

**关键设置**：


其中：

- `-chain_count 6`：请求六条逻辑扫描链。
- `-clock_mixing mix_clocks`：允许不同测试时钟上的扫描单元出现在同一条逻辑链中。

**端点选择方法**：`pad` 是 16 位端口，返回集合按 15 至 0 排列，所以 `15 - i` 对应 `pad[i]`；`sd_A` 是 10 位端口，`9 - i` 对应 `sd_A[i]`。`hookup_pin` 将顶层端口与 I/O 单元指定引脚关联。

| `chain1` | `pad[1]` | `sd_A[1]` | 488 |
| `chain2` | `pad[2]` | `sd_A[2]` | 488 |
| `chain3` | `pad[3]` | `sd_A[3]` | 488 |
| `chain4` | `pad[4]` | `sd_A[4]` | 487 |
| `chain5` | `pad[5]` | `sd_A[5]` | 487 |

### Lab 10：三种层次化扫描流程

**目标**：在同一 ORCA 设计上理解自顶向下、bottom-up（自底向上）和接口模型流程各自保存什么信息，以及为什么完整 ATPG 必须使用完整门级网表。

**三种流程**：

| 流程 | 顶层看到的模块内容 | 适合的检查 | 本次完整 ATPG 结果 |

| bottom-up | 已插入扫描的 13 个模块测试模型；`RESET_BLOCK` 使用完整实现 | 模块先完成扫描处理，再由顶层完成跨模块连接 | 98.63%，372 个向量（277 个 basic scan、95 个 fast sequential） |

**bottom-up 的关键点**：每个模块先运行 `insert_dft`、`write_test_model`，再由顶层读入测试模型。顶层仍要为 `RESET_BLOCK` 读入完整 DDC，因为顶层插入会向该模块加入扫描输入端口。若不在顶层插入后重新写出 `tmax/RESET_BLOCK_gates.v`，TestMAX 会发现网表与 SPF 的端口不一致。

**本次观察**：自顶向下六条链长度为 488、488、488、488、487、487；bottom-up 六条链长度为 1024、590、529、326、266、223。两种完整网表均由 TestMAX 成功追踪全部扫描链并完成 DRC。链长度不同来自模块扫描处理和顶层连接方式不同，不代表其中一种流程失效。

> [!note] 学习提示
> bottom-up 流程中 DFTC 的 38.51% 覆盖率估算只分析可见的测试模型边界，不能与完整门级网表的 TestMAX 98.63% 直接并列解释。判断整芯片 ATPG 时，应查看 `tmax/orca_bottom_up_tmax.log` 的 TestMAX 统计。

## 学习检查题与参考答案

### 问题 1：为什么 `preview_dft` 和 `insert_dft` 都要运行？

`preview_dft` 给出计划的扫描结构，可在改动网表前确认链数、端点、长度和 test point。`insert_dft` 才把扫描单元和新增逻辑写入设计。先预览能够尽早发现端口、时钟或链数设定错误。

### 问题 2：为什么 Lab 5 要先声明 `TEST_MODE`？

`TEST_MODE` 使工具能够在测试时固定部分功能控制逻辑的状态。没有该定义时，时钟和复位的控制条件可能无法确定，从而出现 D1、D3、D15。声明常量后再重建协议，DRC 才会按测试状态分析设计。

### 问题 3：为什么 Lab 7 的 AutoFix 能从 422 项降到 0 项？

修复前的主要问题是不可控时钟和复位。AutoFix 为这些控制点加入由 `TEST_MODE` 选择的测试控制逻辑，并使用 `Clk`、`Reset` 作为 TestData。重建协议并插入后，工具能在测试期间控制相关信号，因此 D1、D3 消失。

### 问题 4：六条逻辑链为什么在 SCANDEF 中变成九个条目？

跨时钟的逻辑链会因 lock-up latch 和时钟条件分为多个物理实现分区。`chain1`、`chain3`、`chain4` 各分成多个条目，总计为 9。逻辑链数和 SCANDEF 条目数不必相同；以 `check_scan_def` 的有效性统计为准。

### 问题 5：为什么 DFTC 的 92.02% 与 TestMAX 的 96.39% 不同？

DFTC 使用内部估算方式；TestMAX 读取导出的网表、SPF 和 RAM 模型后真正生成 pattern。再启用 fast sequential ATPG 后，TestMAX 还能通过多捕获周期覆盖一部分普通 basic_scan 未检出的故障，因此统计不同。

### 问题 6：TestMAX DRC 有 1,321 项内容，为什么仍能完成 ATPG？

DRC 中部分内容是警告，不会阻止工具继续生成 pattern；工具也会在日志中提醒这些 pattern 可能在仿真中出现问题。完成 ATPG 说明文件读入、扫描操作和算法运行成功，不表示所有项目级测试问题已经解决。

### 问题 7：为什么 Lab 10 bottom-up 的 DFTC 估算仅为 38.51%，而 TestMAX 为 98.63%？

bottom-up 顶层在 DFTC 中主要读取各模块的测试模型，内部故障不可见，故 DFTC 只能对可见边界作有限估算。TestMAX 使用重新导出的完整顶层门级网表和所有模块门级网表，因此能够分析模块内部扫描单元。两种结果使用的设计内容不同；整芯片结论应查看完整门级网表的 TestMAX 结果。

### 问题 8：Lab 12 为什么有 5 条外部链、30 条内部链和 37 个 SCANDEF 条目？

5 条外部链是芯片测试引脚侧的串行接口数。压缩器把测试数据展开到 30 条内部扫描链，缩短移位长度。SCANDEF 还会把跨时钟区域、lock-up latch 附近的物理实现段单独记录，所以其条目数可以多于 30。这里的关键检查是 `check_scan_def` 给出 37 有效、0 失败，而不是要求三个数字相同。
