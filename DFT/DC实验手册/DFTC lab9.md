# 实验 9：扫描插入的运行时间、容量与链平衡

## 实验目标

完成本实验后，应能够：

- 在自顶向下扫描插入流程中实现 RSS，得到平衡扫描链。
- 修改自底向上流程，使完整门级设计使用测试模型和 RSS。
- 在块级扫描插入后预览顶层链平衡，并按需要修改块级架构。
- 分析 DFTC 估算覆盖率与实际覆盖率。

**实验时长**：约 75 分钟。

## 任务和目录

### 任务

1. 执行默认的自顶向下扫描插入。
2. 修改扫描规格以获得平衡链。
3. 修改自底向上脚本以使用测试模型。
4. 修改块级扫描以改善顶层平衡。
5. 分析估算覆盖率与实际覆盖率。

## 任务 1：自顶向下扫描插入

### 1. 修改目标

打开 scripts/top_down.tcl，使用课程介绍的 RSS 特性修改脚本。修改后的脚本应满足：

- 尽量少改变原设计。
- 更快完成扫描插入。
- 消耗更少内存。

```
cd lab9_hicap

```

## 任务 1 问题 1–3

### 问题 1

**问题**：第一次运行后的扫描链是否平衡？如果不平衡，为什么？

**参考答案**：通常不平衡。默认自顶向下分配受到测试时钟域、扫描单元数量、原有层次和默认 chain_count 的影响；不同域的触发器数量差异会让某些链远长于其他链。测试时间由最长链决定，因此必须继续优化。

### 问题 2

**问题**：修改 top_down.tcl 后，扫描链是否更平衡？

**参考答案**：应当更平衡。验收标准是查看 preview_dft 报告，比较最长链、最短链和链长标准差，而不是只看链数。

### 问题 3

**问题**：为了获得平衡链，DFTC 添加了什么 DFT 结构？

**答案**：lock-up latch。跨不同测试时钟/边沿的扫描段需要锁存器隔离移位时序；测试时钟越多，出现 lock-up latch 的概率越高。

## 任务 1 问题 4–6

### 问题 4

**问题**：插入了多少个 lock-up latch？

**答案/操作**：使用以下命令统计：

```
sizeof_collection [get_cells LOCKUP* -hier]
```

具体数量取决于本次运行的脚本和库，操作说明没有固定给出单一数字。应把命令输出写入实验报告。

### 问题 5

**问题**：lock-up latch 位于 ORCA 层次的哪里？

**答案/操作**：

```
get_cells LOCKUP* -hier
```

它们应位于跨时钟域或跨块扫描边界附近。若采用 top-down 布局，顶层位置通常不是主要问题；若采用 bottom-up 布局，则应避免在不希望出现的顶层位置插入锁存器。

### 问题 6

**问题**：ORCA 的估算测试覆盖率是多少？

**答案/操作**：

```
dft_drc -coverage_estimate
```

该步骤的数值取决于当前运行；应读取 reports/ORCA_coverage.rpt，记录 total faults、detected、untestable 和 coverage。

## 任务 2：使用测试模型的自底向上扫描

自底向上流程先对子模块执行扫描插入并生成测试模型，再用测试模型完成顶层拼接：

```
scan_blocks.tcl
    读入每个子模块
    执行块级扫描插入
    保存 DDC 和 test_models/*.model
    清理当前块

scan_top.tcl
    先读入测试模型
    再读入包含这些模型的顶层块
    进行顶层扫描拼接
```

ORCA 顶层包含 I/O pad、CLOCK_GEN（PLL 和时钟倍频）以及 ORCA_TOP 核心块。测试模型减少顶层读入的门级细节，从而降低内存和运行时间。

### 脚本修改重点

1. 在 scan_blocks.tcl 的 foreach 循环中，保存独立的测试模型文件。
2. scan_top.tcl 只从 test_models 目录读取模型。
3. 不要把 RESET_BLOCK 当成测试模型；应从 `mapped_scan` 目录读入 RESET_BLOCK 的设计。
4. 用 current_design、link 检查顶层当前设计。

## 任务 2 问题 7–10

### 问题 7

**问题**：为什么块级扫描插入要指定 clock_mixing io_mix？

**参考答案**：块级设计可能包含多个本地测试时钟，允许合适的时钟混合可以避免把每个时钟域机械地拆成大量短链，并让块级链在顶层拼接时更容易平衡。实际值需通过当前版本的 `set_scan_configuration -help` 核对。

### 问题 8

**问题**：insert_terminal_lockup 对块级扫描插入有什么作用？

**答案**：在块级扫描链末端插入 terminal lock-up latch，为顶层拼接提供稳定边界。这样块级链在离开子模块时已经完成移位时序隔离。

### 问题 9

**问题**：如果每条块级链末端都插入 lock-up latch，顶层块级链之间还需要再插入 lock-up latch 吗？

**答案**：通常不需要重复插入，但必须用顶层 preview_dft、scan_path 和 DFT DRC 验证。若顶层连接再次跨越不同的时钟/边沿，工具仍可能插入额外结构。

### 问题 10

**问题**：运行 bottom_up.tcl 后顶层扫描链是否平衡？若不平衡，为什么？

**参考答案**：第一次通常不完全平衡。原因是块级模型的链数量和长度已经在块级固定，顶层只能拼接这些离散链段；块间链长差异会传递到顶层。

## 任务 2 迭代问题 11–14

### 问题 11

**问题**：哪个命令和设置可以生成更平衡的顶层架构？

**参考答案**：在 scan_blocks.tcl 中调整块级扫描规格，例如 chain_count、clock_mixing 和块级链平衡相关设置，然后重新运行 bottom_up.tcl。验收标准是所有顶层链长度相差不超过约 20 个扫描单元。

### 问题 12

**问题**：包含测试模型时，为什么不能使用 任务 1 中的 get_cells LOCKUP* 方法统计所有 lock-up latch？

**答案**：测试模型隐藏了子模块内部的门级单元，顶层数据库中只有模型边界，不包含内部 lock-up latch 实例。应在生成的 Verilog 网表中用文本搜索统计：

```
grep -i LOCKUP tmax/*.v | wc -l
```

### 问题 13

**问题**：整个 ORCA 中插入了多少 lock-up latch？

**答案/操作**：使用上面的 `grep` 统计。具体数字依赖脚本运行；应报告数量和命中网表文件。

### 问题 14

**问题**：lock-up latch 位于 ORCA 层次的哪里？

**答案/操作**：

```
grep -i LOCKUP tmax/*.v
```

根据命中行判断它们位于块内、块边界还是顶层。bottom-up 流程通常让锁存器更多地保留在块级边界，便于物理实现。

## 任务 2 问题 15–18

### 问题 15

**问题**：这与 任务 1 自顶向下脚本插入的 lock-up latch 数量相比如何？

**参考答案**：不要求两者相同。自顶向下直接优化全芯片链；自底向上受到块级模型边界和 terminal lock-up 的影响，数量及位置可能不同。应比较两个流程的网表统计、链长和 DRC，而不能只比较一个数字。

### 问题 16

**问题**：自底向上估算覆盖率与自顶向下估算相比如何？

**参考答案**：应读取两个 coverage report 对比。若差异较大，优先检查测试模型是否完整、块级协议是否一致、黑盒范围和锁存器模型是否正确。

### 问题 17

**问题**：为什么使用测试模型得到的估算覆盖率没有充分意义？

**答案**：测试模型抽象了块内部的门级故障和逻辑可观测性；DFTC 在顶层看到的是模型边界，不是完整故障列表。因此模型下的覆盖率只能用于结构/流程检查，不能替代完整网表上的实际 ATPG。

### 问题 18

**问题**：为什么 TetraMAX 中的总故障数通常比 DFTC 大得多？

**答案**：TetraMAX 读入完整门级网表、RAM/功能模型、测试协议和完整故障模型；DFTC 使用测试模型时会隐藏块内部故障，且故障折叠、黑盒和模型边界不同，所以 TetraMAX 的故障总数通常更大。

## 问题 19

### 问题 19

**问题**：TetraMAX 为 ORCA 得到的测试覆盖率是多少？

**答案/操作**：

```
cd tmax
tmax -shell orca_tmax.tcl
```

然后从 Pattern Summary Report 记录 coverage。该步骤没有固定数值；应以当前实验运行的 TetraMAX 报告为准，不要把实验 7 的 95.28% 或实验 8 的 96.72% 写入实验 9 的结果。
