# Spec 编写指南

> [!abstract] 文档目的
> 本文定义通用 Spec 的编写结构、信息深度、Markdown 格式、图示、术语和审阅要求。它适用于系统、硬件、模块、接口、软件、驱动、Runtime、验证和运维设计文档。本文与 [[术语、用词与语言风格约束]] 配套使用；该文档规定术语和语言限制，本文规定如何把定型设计组织成可实施、可检查的规格。

| 项目 | 内容 |
| --- | --- |
| 文档性质 | Spec 编写知识库 |
| 适用对象 | 产品、架构、硬件、软件、验证、运维和集成开发者 |
| 适用文档 | 系统 Spec、模块 Spec、接口 Spec、数据 Spec、软件设计 Spec、部署 Spec 和验证规格 |
| 编写目标 | 使读者只依赖文档即可理解设计意图、接口、数据组织、时序、错误处理和验证范围 |
| 参考依据 | 项目术语约束、已批准的相关 Spec 和当前定型设计资料 |

## 1. Spec 的定位与基本原则

### 1.1 Spec 的作用

Spec 是定型设计的共同依据。它必须说明“系统是什么、为何这样划分、输入输出是什么、何时发生什么、异常时怎样处理、软件如何使用、验证如何证明”。Spec 不是需求讨论记录、代码阅读笔记、提交说明或测试日志，也不应成为只列寄存器地址和信号名称的参考表。

一份合格的 Spec 应同时支持下列工作：

| 读者 | 必须能从 Spec 得到的信息 |
| --- | --- |
| 架构人员 | 设计范围、取舍、性能相关结构和模块职责 |
| 实现人员 | 模块输入输出、状态、时序、初始化、错误处理和参数范围 |
| 验证人员 | 可观察结果、异常注入条件、状态转换和覆盖项目 |
| 接口与集成人员 | 协议字段、数据布局、地址规则、完成条件和调用次序 |
| 平台与部署人员 | 资源、权限、环境依赖、初始化和运行要求 |
| 业务或应用开发人员 | 支持的功能、输入输出、结果格式和不支持范围 |

### 1.2 定型描述原则

正文只写当前定型设计。使用“必须、不得、应、可”表示要求强度，并使每个“必须”能够落到接口、状态、字段、时序或验证项目上。

不得在正文中保留早期方案、迭代经过、临时兼容、代码迁移或“以后考虑”的叙述。若某能力未纳入当前设计，应直接写明“不定义”“不支持”或“由指定组件处理”，并说明实际处理方式。

| 不合格表达 | 定型表达 |
| --- | --- |
| 当前版本先按某方案实现 | 本设计采用某方案，并给出接口和限制 |
| 后续可能加入某能力 | 本设计不定义该能力；相关工作由指定模块处理 |
| 旧接口暂时仍可使用 | 对外接口仅定义当前字段和时序 |
| 代码中已经这样做 | 设计规定为这样做，并给出可检查条件 |

### 1.3 完整性原则

Spec 应以读者不查看实现代码为前提。任何影响正确性、互操作性或验证结果的事实，均不得只存在于代码或口头约定中。以下信息必须进入正文或表格：

1. 对外可见的参数、端口、寄存器、指令、数据格式和地址规则；
2. 模块之间的数据、控制、完成和错误关系；
3. 状态转换、交互、暂停、初始化、停止和恢复行为；
4. 存储单位、字节顺序、对齐、布局、容量和访问范围；
5. 不支持的操作、形状、格式或调用方式；
6. 调用方必须完成的准备动作和服务端或设备必须提供的终态结果；
7. 验证应覆盖的正常、极限和异常情形。

## 2. 文档总体结构

### 2.1 内容模块与组合原则

Spec 不规定固定章节名称、编号或顺序。作者应根据设计对象选择下表中的内容模块，并按“读者先理解对象和范围，再理解规则、细节和验证”的顺序组织。没有实际内容的模块不得保留为空标题；对设计正确性有影响的内容模块不得省略。

| 内容模块 | 适用场景 | 必须回答的问题 |
| --- | --- | --- |
| 文档目的与适用范围 | 所有 Spec | 文档定义什么，适用谁，与哪些资料配套 |
| 术语、角色与约定 | 存在专业术语、多个参与方或缩略语 | 对象如何命名，角色分别负责什么 |
| 目标、限制与假设 | 系统、产品、模块和软件设计 | 需要满足什么，明确不支持什么，依赖哪些前提 |
| 架构与职责 | 包含多个组件、服务或层次 | 各组件如何连接，谁负责什么，主要对象如何流动 |
| 接口与数据契约 | 公开端口、协议、API、文件或消息 | 交互对象、字段、有效条件、错误和兼容规则是什么 |
| 状态、流程与时序 | 有生命周期、异步操作、事务或调用顺序 | 何时开始、等待、完成、暂停、恢复或失败 |
| 配置、资源与存储 | 存在容量、地址、权限、成本或部署资源 | 参数来源、有效范围、布局、占用和释放规则是什么 |
| 功能与算法 | 存在指令、操作、策略、公式或数据处理 | 输入如何变成输出，数值和异常行为是什么 |
| 安全、错误与恢复 | 存在权限、错误、超时或故障 | 如何检测、报告、隔离、清理和恢复 |
| 端到端场景 | 多组件协作 | 从请求到结果的完整次序和可观察结果是什么 |
| 验证与验收 | 所有定型设计 | 如何证明正常、极限和异常行为符合定义 |
| 定型约束汇总 | 参数较多或容易误用 | 哪些固定条件最需要快速查找 |

模块级 Spec 可以只选择“目的与范围、架构与职责、接口与数据契约、状态与流程、错误与恢复、验证”六类内容模块。即使文档只覆盖一个组件，也必须说明其输入、输出、依赖对象和外部可观察行为。

### 2.2 章节粒度

一个标题只描述一个中心主题。若同一章同时讨论接口字段、状态机和测试结论，应拆成相邻小节。标题使用名词短语或明确问题，例如“地址引用格式”“读功能时序”“任务确认”“缓存一致性”，不使用“其他说明”“补充内容”“若干问题”等空泛标题。

推荐层级如下：

```markdown
# 文档标题

## 1. 一级主题

### 1.1 二级主题

#### 1.1.1 仅在需要独立规则或公式时使用
```

若使用数字标题，编号必须连续；若项目采用无编号标题，也必须保持层级清晰。标题下应先给出一句至一段概述，再给出表格、规则、公式、图示或时序；不要让读者先看到没有解释的长表。

### 2.3 标题、摘要和文档信息

标题必须准确说明文档对象和层次。例如，可使用“支付结算接口 Spec”“缓存服务设计”“某模块设计 Spec”或“数据交换格式说明”。不要在标题中加入版本沿革、人员名称或临时工作状态。

摘要使用 `> [!abstract]` 提示块，集中说明以下内容：

1. 文档定义的设计对象；
2. 覆盖的技术范围；
3. 读者可将其作为哪些工作的输入；
4. 与其他关键 Spec 的关系。

标题后应给出文档信息表。最少包含文档状态、适用对象、基准结构或基准配置、参考文档。若文档只定义一个模块，可把“基准结构”替换为“所在系统位置”。

```markdown
# 模块设计 Spec

> [!abstract] 文档目的
> 本文定义……，说明……，可作为……工作的共同依据。

| 项目 | 内容 |
| --- | --- |
| 文档状态 | 设计规格 |
| 适用对象 | 设计、实现、验证和集成 |
| 基准结构 | 设计对象所在的系统位置和相邻组件 |
| 参考文档 | [[相关 Spec]] |

---
```

## 3. 文档约定、范围与参数

### 3.1 规范用语

文档应在“约定”或等效内容模块中定义“必须、不得、应、可”。同一文档不得把“应”写成强制要求，也不得使用“尽量”“通常”“视情况”等无法验证的词替代要求强度。

| 用语 | 使用方式 |
| --- | --- |
| 必须、不得 | 用于接口时序、字段取值、存储范围、复位结果和错误处理等不可改变的规则 |
| 应 | 用于默认方案、性能建议或可替代实现；改变时需说明影响 |
| 可 | 用于不改变基础正确性的附加能力，并写明启用条件 |

### 3.2 缩略语和正式名称

缩略语首次出现时应写为“缩写（English Full Name，中文名称）”，后续才可单独使用。行业通用名称按 [[术语、用词与语言风格约束]] 直接使用。每个模块只有一个正式名称；图示、标题、正文、端口表和软件接口必须使用相同名称。

缩略语表应只收录正文确实使用、且读者需要确认含义的名称。不要为了凑表格加入没有出现在正文的缩略语，也不要为一般英文词临时创造新缩写。

### 3.3 设计范围与不支持项

设计范围应列出本文覆盖的模块、接口、操作、格式和时序。范围外事项应写明当前由谁处理或为何不定义，避免让读者误以为缺少内容是疏漏。

| 表达目标 | 推荐写法 |
| --- | --- |
| 明确覆盖 | “本文覆盖……、……和……。” |
| 明确不定义 | “本文不定义……；该工作由……处理。” |
| 明确限制 | “本设计只接受……；其他取值在提交前返回……。” |
| 说明参数来源 | “该参数由构建配置确定，不是调用期可写设置。” |

范围章节不得使用仓库目录、实现文件、实例层次或提交记录来界定设计对象。使用正式模块名称、接口名称、指令名称和软件组件名称描述范围。

### 3.4 基准配置与参数表

凡是影响接口、布局、性能、容量或验证的固定参数，必须在首次使用前或统一的配置内容模块中列出。参数表至少包含名称、符号或正式参数名、基准值、状态和说明。

| 参数表列 | 编写要求 |
| --- | --- |
| 参数 | 使用正式中文名 |
| 符号或参数名 | 使用公式符号、正式配置名或 API 参数名 |
| 基准值 | 带单位，或明确为枚举值、范围、位宽 |
| 状态 | 说明是定型值、构建参数、用户要求或参考配置 |
| 说明 | 写出影响范围、软件可见性和不可改变的条件 |

参数说明必须区分构建配置、部署配置和调用期可写设置。若某值只用于模拟、压测或验证，必须标记为参考配置，并说明它不会改变对外契约和功能规则。

## 4. 架构、模块职责与图示

### 4.1 总体结构章节

总体结构章节先用一段话说明系统的输入、输出和分层，再给出图示和职责表。图示用于展示模块关系；职责表用于说明每个模块实际负责的工作。二者不可互相替代。

大模块关系图必须包含：

1. 外部调用方、依赖服务、存储系统、网络或用户界面；
2. 本设计的大模块及其正式名称；
3. 控制、数据、完成或错误的主要方向；
4. 与子模块的从属关系，或在相邻子图中给出该关系；
5. 读者理解数据单位、执行环境、存储位置、权限或调用顺序所必需的标注。

每个大模块应有一张自身与子模块关系的图，或在一张分区清楚的大图中完整表示其子模块。图形过大时，应以“系统总图 + 模块局部图”代替把全部模块塞进一张图。

### 4.2 图示编写规则

| 项目 | 要求 |
| --- | --- |
| 模块名称 | 使用正文中的正式名称，不使用实例名、临时简称或实现目录名 |
| 方框内容 | 只放模块名称和一行职责摘要，复杂规则留给正文 |
| 箭头 | 表示明确的控制、数据、完成或错误方向；双向关系使用两条单向箭头或清晰的双向箭头 |
| 标签 | 标签必须与方框、箭头和外框留出空白，不得发生遮挡 |
| 字号 | 在文档默认显示宽度下可读；长名称应扩大方框或换行，不缩小到不可读 |
| 配色 | 使用少量稳定颜色区分模块类别；颜色不能成为唯一的信息来源 |
| 图题 | 紧随图示，写明图号和图所说明的关系 |

绘图完成后必须导出实际显示格式并目检。检查项目包括中文字体是否缺字、文字是否压住边框、箭头是否穿过文字、左右区域的标签是否贴近外框、长边比例是否导致阅读困难。图示编辑源应随文档保留，便于修改模块名称和连接关系。

### 4.3 模块职责表

总体结构图后必须列出大模块职责。推荐使用下表结构：

| 模块 | 输入 | 输出 | 必须完成的工作 | 不负责的工作 |
| --- | --- | --- | --- | --- |
| 正式模块名 | 明确接口或数据对象 | 明确接口或数据对象 | 写出该模块必须做出的决定或动作 | 写明由其他模块承担的事项 |

“不负责的工作”一列对于软件、控制和存储模块尤其重要。它可以避免把模型图解析、地址分配、任务调度、数据格式转换和硬件执行混写为同一模块职责。

### 4.4 主要数据与控制关系

总体章节应在图示后用表格或编号列表说明主要关系。每一项应包含来源、去向、对象、触发条件和结果。例如：

| 来源 | 去向 | 对象 | 触发条件 | 结果 |
| --- | --- | --- | --- | --- |
| 编译器 | Runtime | 静态命令与绑定记录 | 模型调用开始 | Runtime 可准备 DMA 内存区 |
| Runtime | 驱动 | 批次提交请求 | 地址配置和 Cache 同步完成 | 驱动向命令 FIFO 写入命令 beat |
| 执行单元 | 任务调度模块 | 完成状态 | 当前任务完成或出错 | 更新任务终态并释放等待者 |

该表的目的不是重复端口表，而是解释跨模块动作的因果关系。

## 5. 接口、端口、寄存器与软件 API

### 5.1 接口章节的共同要求

接口章节必须先说明接口类型、交互环境、传输粒度、事务顺序和错误返回，再给出信号、字段、配置项或 API 表。标准协议行为、项目内部扩展和验证环境检查必须分别说明，不得把内部字段写成标准协议固有字段。

接口说明必须回答以下问题：

1. 谁发起访问，谁接收访问；
2. 每次传输的数据单位、字节顺序和地址单位是什么；
3. 哪些信号、字段或函数参数构成一次有效请求；
4. 接收方何时接受、何时暂停、何时返回结果；
5. 复位、停止、非法输入、超时和下游错误时发生什么；
6. 哪些数据必须在握手前稳定，哪些数据可在何时改变；
7. 软件需要先后执行哪些操作，才能得到可读取结果。

### 5.2 硬件端口表

端口表必须一行一个信号，并使用以下列：

| 信号 | 方向 | 位宽 | 功能 | 有效条件 | 暂停、错误与复位行为 |
| --- | --- | ---: | --- | --- | --- |
| `SIGNAL_NAME` | 模块输入或模块输出 | 明确位数或参数表达式 | 该信号传递或控制的内容 | 有效信号、握手或采样条件 | 暂停时保持规则、错误响应和复位状态 |

不得将 `VALID` 与 `READY` 合并成一行；两者方向不同且各自承担不同责任。数组信号应说明单个成员位宽、数组数量和索引范围。若时钟复位、标准总线、内部请求、调试统计属于不同接口类别，应分表说明。

端口表之后必须补充时序文字。例如，对 ready/valid 接口至少明确：发送方在 `VALID=1` 且未握手时保持地址、数据、字节使能和操作码不变；接收方可通过 `READY=0` 暂停；传输只在两者同为 1 的采样沿成立。对于网络、文件或 RPC 接口，应给出等效的请求接受、重试、超时和幂等规则。

### 5.3 CSR 与寄存器表

寄存器、配置或状态表必须写出访问方式、默认值、字段位置、字段含义、合法取值、非法访问结果和调用顺序。一个寄存器或配置对象有多个字段时，应先给总表，再给字段表；不要只给位图或结构定义而省略每个字段的功能说明。

| 寄存器 | 地址偏移 | 访问 | 复位值 | 作用 |
| --- | ---: | --- | --- | --- |
| `REG_NAME` | 明确字节偏移 | RO、WO 或 RW | 明确数值 | 一句话说明寄存器用途 |

| bit | 字段 | 访问 | 复位值 | 合法取值与作用 | 非法访问或写入结果 |
| --- | --- | --- | --- | --- | --- |
| `x:y` | `FIELD_NAME` | RO、WO 或 RW | 明确数值 | 取值定义和生效时机 | 错误状态、忽略或拒绝规则 |

如果寄存器写入会启动任务、清除错误、确认完成或替换地址配置，必须在其后给出明确的软件操作次序和并发限制。

### 5.4 软件 API 表

驱动、Runtime 和编译器对外 API 应按功能分组。每个 API 至少说明输入、输出、前置条件、成功结果、失败返回和资源责任。

| API | 输入 | 输出 | 前置条件 | 成功结果 | 失败与清理 |
| --- | --- | --- | --- | --- | --- |
| `function_name` | 参数及取值范围 | 返回值和输出对象 | 初始化、对齐、锁或状态要求 | 状态变化与输出内容 | 错误码、对象状态和调用方下一步 |

不得只列函数原型。若 API 依赖 Cache 同步、物理连续内存、锁、硬件启动状态或任务确认，必须在表格和对应流程章节中写明。

### 5.5 地址、对齐与字节顺序

地址规则必须明确以下项目：

| 项目 | 必须说明的内容 |
| --- | --- |
| 地址宽度 | 实际接受的 bit 数及高位必须为零的条件 |
| 地址单位 | 字节地址、word 地址或经过单位移位的地址引用 |
| 对齐 | 每类访问、命令、数据结构或面板所需的最小对齐 |
| 访问跨度 | 首地址、元素数、步长和最后一个字节的检查方式 |
| 字节顺序 | 多字节整数在低地址和高地址的保存顺序 |
| 区域选择 | 区域编号、区域内偏移、基址配置和容量检查 |
| 非法结果 | 对齐错误、越界、保留编码和地址窗口外访问的错误状态 |

只写“地址必须合法”是不够的。应给出字段宽度、单位、公式或具体范围，使编译器、驱动和验证能独立检查最后访问字节。

## 6. 指令、数据格式和存储布局

### 6.1 指令章节结构

有指令集的系统应把指令体系集中在一个完整章节。推荐顺序如下：

1. 执行模型和命令生命周期；
2. 总线或 FIFO 上的命令提交次序；
3. 公共命令头、标志、编号、超时和 Event；
4. 地址引用格式与数据格式编码；
5. 指令总表；
6. 每条操作的参数域位段、限制和计算结果；
7. 字段检查、错误状态和完整编码示例。

每条指令应明确 opcode、适用执行单元、输入输出数据格式、参数域 bit 位置、保留 bit、尺寸范围、地址对齐、完成条件和错误结果。不能只给枚举名称或只给计算公式。

### 6.2 指令总表与位段表

指令总表用于快速查找，专用位段表用于精确实现。推荐格式如下：

| opcode | 指令 | 执行单元 | 输入与输出 | 作用 | 主要限制 |
| ---: | --- | --- | --- | --- | --- |
| 明确编码 | 正式指令名 | 正式执行单元名 | 数据格式和对象 | 一句话定义结果 | 尺寸、格式或状态限制 |

| bit | 字段 | 编码 | 含义 | 取值限制 |
| --- | --- | --- | --- | --- |
| `x:y` | 正式字段名 | 位宽或枚举 | 对计算和访问的影响 | 合法范围、保留值和错误结果 |

位段表必须覆盖全部 bit。保留字段应明确为零，且写出硬件对非零值的处理。若同一字段对不同 opcode 有不同含义，应分指令列出，不要用含混的“按操作解释”。

### 6.3 计算公式与数值行为

涉及算术、统计、激活、舍入、饱和、截断或格式转换时，应同时给出数学公式和整数实现规则。公式之后必须说明：

1. 输入与输出张量形状和轴；
2. 输入、内部累加和输出数据格式；
3. 符号扩展、右移、舍入和饱和的顺序；
4. 溢出、除零、空维度、非法格式和不支持尺寸的结果；
5. 使用的近似函数、查表或内部浮点计算是否对软件可见。

示例应选择小尺寸、可手算的整数输入，逐步展示地址或矩阵元素的结果。示例用于消除歧义，不能取代完整字段与公式定义。

### 6.4 数据格式表

数据格式必须独立成表，至少写出编码、位宽、数值范围、符号、字节顺序、典型用途和不允许的用途。

| 格式 | 编码 | 位宽 | 数值范围 | 存储规则 | 允许用途 | 不允许用途 |
| --- | ---: | ---: | --- | --- | --- | --- |
| 正式格式名 | 指令编码 | 明确位数 | 明确范围 | 小端、对齐或打包规则 | 输入、权重、累加或输出 | 明确禁止的对象 |

若内部使用的格式与软件可见格式不同，必须明确区分。例如，内部 FP32 状态不意味着软件可将模型张量声明为 FP32。

### 6.5 存储布局章节

存储布局必须面向字节与元素说明，不能只写“按 tile 排列”。对每种布局应给出：

| 项目 | 必须说明的内容 |
| --- | --- |
| 逻辑对象 | 原始矩阵、张量、索引或结果的形状与行列约定 |
| 物理排列 | tile 顺序、tile 内顺序、行列步长、K 组或通道组顺序 |
| 字节数 | 精确公式、对齐和尾部填充规则 |
| 地址公式 | 逻辑下标到字节偏移的计算方式 |
| 读写方 | 哪个模块或软件层生成、读取和还原该布局 |
| 合法范围 | 形状、数据格式、对齐、地址和尾部条件 |

布局涉及硬件专用面板时，必须同时给出普通行主序源对象、打包结果、硬件读取对象和结果还原对象之间的关系。编译期准备和调用期转换也应分别说明。

## 7. 大模块章节的标准写法

### 7.1 每个模块的最小内容

每个大模块章节应按下列次序展开。实际实现不需要机械地使用相同标题，但信息不可缺失。

| 小节 | 必须写明的内容 |
| --- | --- |
| 定位与职责 | 模块在系统中的位置、上游下游、完成的唯一职责和不负责事项 |
| 子模块关系 | 子模块名称、连接方向、各子模块职责和共享资源 |
| 参数与容量 | 位宽、深度、容量、队列项数、并发数、构建参数和软件可见性 |
| 模块接口 | 端口表或内部请求表；有效条件、暂停、错误和复位行为齐全 |
| 输入检查 | 字段、地址、格式、状态或资源条件的检查次序 |
| 状态与时序 | 状态机、握手、请求发起、响应接收、完成和错误时刻 |
| 存储与数据 | 缓冲区、地址计算、字节顺序、生命周期和复用条件 |
| 异常与复位 | 错误码、停止、复位、未完成请求和状态清除规则 |
| 软件关系 | 编译器、驱动或 Runtime 需要做的准备、查询与确认动作 |
| 验证要求 | 正常、暂停、越界、格式错误、复位和极限容量的覆盖项目 |

### 7.2 状态机与功能时序

只列状态名称是不够的。状态机说明必须写明进入条件、每个状态的动作、退出条件、错误转移、停止转移和复位初值。对于异步请求，应说明请求握手后何时允许下一请求、响应是否可能乱序、响应到达后更新何种状态，以及完成通知在何时对查询接口可见。

| 状态 | 进入条件 | 状态内动作 | 正常退出 | 异常或停止退出 |
| --- | --- | --- | --- | --- |
| `STATE_NAME` | 上一个状态的明确条件 | 请求、计数、寄存器更新或等待动作 | 下一状态及条件 | 错误状态、停止状态或复位行为 |

功能时序可用编号步骤、时序表或波形图说明。应区分“接受请求”“开始执行”“结果已写入”“完成状态可查询”“中断可见”这几个可能不同的时刻。

### 7.3 仲裁、资源和暂停

共享存储、总线、执行单元、队列、任务槽或锁的模块，必须写明仲裁对象、优先顺序、公平性规则、暂停条件和响应归属。不要只写“按优先级仲裁”。

至少应明确：

1. 可同时存在多少个请求或任务；
2. 满时如何拒绝、暂停或报告错误；
3. 相同优先级请求如何选择；
4. 已接受请求的响应返回给谁；
5. 停止和复位时队列、计数器和等待请求如何处理；
6. 软件是否可观察等待、占用或错误状态。

### 7.4 错误与完成

每个可失败模块都必须定义错误的来源、检测时刻、保存位置、上报路径和恢复方式。错误编码表应覆盖非法字段、地址对齐、范围越界、数据格式、依赖失败、资源不足、总线错误和超时等与模块有关的情形。

| 错误 | 触发条件 | 可观察位置 | 对当前操作的影响 | 软件或上游恢复动作 |
| --- | --- | --- | --- | --- |
| 正式错误名 | 精确非法条件 | 状态位、响应或任务终态 | 拒绝、停止或失败完成 | 查询、确认、清除、复位或重新提交 |

完成与错误应具有明确关系。例如，错误任务是否仍产生完成记录、是否需要确认、是否唤醒等待任务、是否可重用编号，都必须写明。

## 8. 软件、服务与自动化流程的专用要求

### 8.1 分层与职责

软件或服务 Spec 应将用户入口、输入适配、业务或任务规划、执行运行时、外部服务适配和平台服务分开描述。每层必须明确输入、输出、调用环境、状态保存、资源管理和不承担的工作。实际系统没有某一层时，不应为了套模板而增加该层。

| 层或组件 | 典型输入 | 典型输出 | 不应承担的工作 |
| --- | --- | --- | --- |
| 用户入口 | 请求、配置或用户数据 | 已验证的调用请求 | 直接处理底层资源细节 |
| 输入适配 | 外部格式或协议 | 统一业务对象 | 执行与输入无关的业务决策 |
| 规划或生成组件 | 业务对象与配置 | 任务、计划、交付物或调用记录 | 决定部署环境的实际资源位置 |
| 执行运行时 | 已定义任务与调用参数 | 本次调用结果 | 改变已定型的业务规则 |
| 外部服务适配 | 运行时请求 | API、消息、文件或设备访问 | 解析完整业务流程 |
| 平台服务 | 适配请求 | 存储、网络、认证、日志或计算资源 | 修改上层的数据契约 |

### 8.2 生成、构建或编排流程

当设计包含代码生成、工作流编排、任务计划或构建过程时，应说明输入格式、检查规则、支持能力、选择规则、资源计划、交付内容和离线错误。对每种输入类型或任务类型，必须明确它被本系统处理、交给外部服务处理，还是直接拒绝。

| 阶段 | 输入 | 处理 | 输出 | 失败条件 |
| --- | --- | --- | --- | --- |
| 接入与检查 | 请求、配置和静态数据 | 名称、格式、权限、依赖和属性检查 | 已验证对象 | 缺失、冲突、非法格式或权限不足 |
| 规划 | 已验证对象 | 任务拆分、依赖排序、资源估算 | 执行计划 | 不支持能力或资源不足 |
| 准备 | 执行计划 | 数据准备、配置展开、外部对象创建 | 可执行调用 | 地址、容量、配额或参数超限 |
| 交付或发起 | 可执行调用 | 编码请求、写入交付内容或发起事务 | 结果记录 | 字段、版本或前置状态非法 |

相关 Spec 不得把“根据实现代码可知”作为接口定义。所有交付对象必须说明名称类别、字段、字节数或大小、生成方、消费方及其中的稳定内容。

### 8.3 运行时与集成章节

运行时、客户端、驱动或集成层章节应定义公开契约、用户输入、环境要求、调用流程、并发控制、重试、清理顺序和错误返回。若涉及外部设备、远端服务或数据库，还应说明连接建立、认证、超时、重连和可恢复性。

对一次完整调用，必须给出从“检查输入”到“释放资源或提交结果”的完整顺序。错误路径必须与正常路径同样完整，至少说明已建立连接、已创建临时对象、已取得锁和已分配资源如何清理。

### 8.4 调用期数据与一致性

软件或服务 Spec 必须明确不同执行方何时可读取、写入或修改同一数据对象。对输入、临时数据、持久数据、输出和缓存对象，说明数据准备、可见性、提交、失效、回滚和清理条件。

| 数据对象 | 调用方准备 | 服务端或设备访问 | 写入完成条件 | 调用方读取前 |
| --- | --- | --- | --- | --- |
| 输入数据 | 创建、复制或校验 | 仅在请求接受后读取 | 通常不修改原始输入 | 验证响应状态和版本 |
| 临时数据 | 初始化或打包 | 在任务运行期间读写 | 任务成功、失败或取消时明确处理 | 检查有效期并按规则清理 |
| 输出数据 | 可预先创建占位对象 | 服务端写入或返回 | 完成状态确认后有效 | 检查状态、一致性和访问权限 |

### 8.5 软件错误与资源责任

软件 API 的错误表应区分参数错误、范围错误、权限错误、资源不足、外部 I/O 错误、超时、冲突和不支持。每个资源均应明确创建方、使用方和释放方；例如，平台提供临时存储，运行时在调用结束时释放，适配层只使用其标识和范围。

不要使用含糊的“自动处理”描述资源责任。应写明谁调用创建、谁执行清理、错误时是否回滚、调用者是否仍可重用对象。

## 9. 端到端场景、角色分工与验证

### 9.1 端到端场景

跨组件 Spec 至少应包含一个正常场景和一个错误场景。场景从用户、外部系统或定时任务发起，经过验证、处理、存储和依赖组件，直到结果可读取、事件可确认或错误可查询。

正常场景应明确：配置、数据准备、请求发起、请求接受、处理、完成、状态查询、结果读取和资源释放。错误场景应明确：错误发生点、停止后续动作、状态记录、清理、重试或恢复条件。

| 次序 | 调用方或上游动作 | 服务端或依赖组件动作 | 可观察结果 |
| ---: | --- | --- | --- |
| 1 | 完成配置与数据准备 | 等待有效请求 | 请求内容、身份和前置状态有效 |
| 2 | 提交请求或事件 | 接受、检查并建立处理记录 | 响应、状态变化或任务标识 |
| 3 | 等待或订阅结果 | 执行处理、访问依赖或返回错误 | 成功、失败、取消或超时状态 |
| 4 | 查询、确认并读取结果 | 清理临时状态或保留审计记录 | 调用方得到结果或明确错误码 |

### 9.2 角色分工表

角色分工表应放在接近端到端场景的位置，避免读者在多个章节中猜测某项决定由谁作出。角色可按实际系统替换为客户端、服务端、后台任务、设备、管理员或外部依赖。

| 事项 | 设计或构建阶段 | 调用方 | 服务端或依赖组件 |
| --- | --- | --- | --- |
| 请求和任务 | 定义输入、规则和计划 | 选择请求并提供参数 | 执行已定义处理 |
| 资源位置 | 定义逻辑标识和容量 | 提供实际环境配置 | 检查权限、范围和可用性 |
| 数据格式 | 定义合法格式和转换规则 | 准备输入数据 | 按契约处理并返回结果 |
| 依赖与完成 | 定义依赖次序和状态名称 | 等待、确认、重试或恢复 | 保存状态并通知订阅方 |
| 错误 | 定义拒绝条件和错误码 | 停止、清理和报告 | 产生可查询错误状态 |

### 9.3 验证规格

验证章节不应只列“已测试”或“覆盖正常功能”。它必须把设计规则转为可执行的覆盖对象，并写出输入条件和期望结果。

| 类别 | 必测情形 | 期望结果 |
| --- | --- | --- |
| 正常功能 | 每类请求、数据格式和典型规模 | 结果、状态和持久数据符合定义 |
| 暂停与重试 | 依赖暂不可用、队列满、网络中断或限流 | 不重复处理，重试与超时符合规则 |
| 极限参数 | 最小值、最大值、容量临界值和并发上限 | 无越界、无资源泄漏，结果符合定义 |
| 非法输入 | 缺失字段、未支持格式、非法枚举和权限不足 | 返回明确错误，不执行未定义操作 |
| 数据与存储 | 冲突写入、版本过期、配额超限和清理失败 | 状态、回滚和审计记录符合定义 |
| 启动停止 | 初始化中断、执行中停止、错误清除和重新启动 | 状态回到定义值，不保留无效处理记录 |
| 集成调用 | 契约版本、参数、超时、清理和恢复 | 返回值、资源释放和用户结果正确 |

性能数据可放入验证章节，但必须给出适用配置、统计区间、包含和不包含的时间段。不能把局部处理时间直接称为完整请求时延，也不能把构建、排队或人工处理时间混入未说明的性能指标。

### 9.4 定型约束汇总

文档最后可用表格汇总最容易被误用的固定条件，例如版本、容量、并发数、超时、数据格式、权限、对齐、兼容范围和不支持项。该表是正文的索引，不替代前面内容模块中的完整定义。

## 10. Markdown、提示块与语言风格

### 10.1 Markdown 格式

普通段落保持自然换行，不在一句话尚未结束时插入手工换行。标题、表格、列表、提示块、公式和图示按 Markdown 结构另起行。一级和二级标题之后保留一个空行；列表和表格前也保留一个空行。

表格中同一列应表达同一类型的信息。数值列右对齐，文本列左对齐。单元格内容较长时优先拆分表格或移至后续段落，不把多段叙述压入一个单元格。

代码、寄存器名、端口名、字段名、指令名、参数名和 API 名使用反引号包围。正文说明使用自然中文，不把源文件名、文件扩展名、仓库路径、实例层次当作设计对象。

### 10.2 提示块的使用

提示块只用于需要被读者优先注意的信息。正文的完整定义仍应位于对应章节中，提示块不能替代字段表、端口表或时序说明。

| 类型 | 适用内容 | 不应用于 |
| --- | --- | --- |
| `> [!abstract]` | 文档目的、范围和共同依据 | 章节内的普通概述 |
| `> [!note]` | 设计理由、术语解释、参数来源或容易误解的背景 | 替代必须遵守的规则 |
| `> [!important]` | 不可违反的定型约束、数值结果、接口关键点 | 一般性的补充材料 |
| `> [!warning]` | 容易造成错误使用的限制、适用范围或异常后果 | 未经说明的风险提示 |

同一内容只在一个位置完整定义。提示块应引用或概括该定义，不应在多个章节复制长篇规则造成不一致。

### 10.3 语言风格

正文使用完整、自然、严谨的专业中文。先定义对象，再说明动作和结果；先给共同规则，再给操作专有规则；先给正常行为，再给异常行为。每个段落应有一个明确主题，避免把设计动机、接口字段、测试结果和仓库操作混在同一段。

推荐使用以下句式：

| 目的 | 推荐句式 |
| --- | --- |
| 定义规则 | “模块必须……；当……时，模块……。” |
| 定义范围 | “本设计只支持……；……不属于本文范围。” |
| 定义时序 | “在……握手后，……在下一周期……。” |
| 定义错误 | “若……，模块建立……终态，并且不得……。” |
| 定义调用动作 | “调用组件在……前必须……，随后……。” |
| 说明原因 | “采用该规则以保证……，并避免……。” |

避免“显然”“一般来说”“通常情况下”“适当处理”“按需”“相关内容”等不提供可检查含义的表述。若必须描述条件，应把条件写成位、数值、状态、接口动作或配置范围。

### 10.4 禁用与限制表达

正文必须遵守 [[术语、用词与语言风格约束]]。其中列出的禁用词只能在本指南这样的词语清单中出现，不得写入设计正文。对含义宽泛的限制词，应替换为更准确的技术表达。

| 不推荐表达 | 推荐表达 |
| --- | --- |
| 地址应正确 | 地址必须 8-byte 对齐，且最后访问字节不超过区域容量 |
| 接口支持暂停 | 当 `READY=0` 时，发送方保持 `VALID`、地址和数据不变 |
| 模块处理错误 | 模块保存错误码，建立失败终态，并阻止当前任务继续发射 |
| 调用方准备数据 | 调用方复制或校验输入，完成一致性操作并提交请求 |
| 数据采用特定布局 | 写明 tile 次序、地址公式、字节数、对齐和尾部填充 |

不得以“代码已经实现”“测试已经通过”“以前版本如此定义”等方式代替规格。设计正文不写仓库操作、提交说明、源文件位置和实现层次。

## 11. 编写、审阅与发布检查清单

### 11.1 编写次序

建议按以下次序编写，而不是从接口细节或代码细节直接开始：

1. 确认当前定型设计、固定参数和明确不支持项；
2. 定义文档范围、读者和与其他 Spec 的关系；
3. 画系统总图及各大模块子图，检查名称和连接方向；
4. 选择实际需要的内容模块，列出组件职责、数据对象、资源和角色分工；
5. 写共同契约、初始化、错误和数据格式规则；
6. 写接口、配置、状态、流程、存储和算法等精确内容；
7. 写完整正常和异常时序；
8. 从每条“必须”提取验证项目；
9. 汇总定型约束，执行术语、格式、交叉引用和图示检查。

### 11.2 内容审阅清单

发布前逐项检查：

- [ ] 标题、摘要、文档信息表、规范用语、缩略语和范围是否齐全；
- [ ] 是否只描述当前定型设计，没有版本沿革、临时方案或仓库操作；
- [ ] 所有大组件是否有职责表，并以图示说明与子组件或依赖对象的关系；
- [ ] 所有公开端口、API、消息或数据对象是否包含有效条件、暂停、错误和初始化行为；
- [ ] 所有配置、字段、操作和 API 是否给出了完整取值范围和失败结果；
- [ ] 涉及地址、对齐、字节顺序、容量、版本或权限的规则是否可独立检查；
- [ ] 是否区分了设计期、调用期、服务期和运维期的职责；
- [ ] 是否定义了正常、暂停、错误、超时、停止、恢复和初始化时序；
- [ ] 每个错误是否能说明检测位置、可观察状态、当前操作结果和恢复动作；
- [ ] 验证章节是否包含极限值、非法值、暂停和资源清理；
- [ ] 汇总表是否与正文数值、位宽和限制一致。

### 11.3 格式与语言审阅清单

- [ ] 标题编号连续，标题只描述一个主题；
- [ ] 缩略语首次出现已给出全称和中文说明，通用名称按术语约束直接使用；
- [ ] 术语、模块名、端口名、指令名、字段名和图示标签前后一致；
- [ ] Markdown 段落、标题、表格、列表和提示块之间保留正确空行；
- [ ] 表格列名准确，数值、单位、bit 位置、地址单位和对齐要求完整；
- [ ] 提示块只用于摘要、说明、关键约束或警告，没有替代完整定义；
- [ ] 正文未出现禁用词、含义宽泛的限制词、源文件名、实现目录或实例层次；
- [ ] 图中文字在默认显示尺寸下清晰可读，未与方框、箭头或外框重叠；
- [ ] 图示、表格、公式和正文中的数值、名称、方向和状态一致；
- [ ] 交叉引用均指向现有且名称准确的文档或章节。

### 11.4 修改已有 Spec 时的额外检查

修改已有 Spec 必须以当前实际设计为唯一依据。修改前先核对所有受影响组件、接口和验证资料；修改后检查是否仍残留被替换的组件、规则、参数、图示、表格、限制或测试描述。

不要在原文中追加“更新说明”“兼容说明”或旧方案对比来保留迭代痕迹。应直接在原位置替换为新的定型内容，并同步更新受影响的图示、接口表、配置表、角色分工表和验证要求。

## 12. 可组合模板

下列模板提供所有 Spec 共有的开头，以及可按设计对象选择、改名、合并、排序或省略的内容模块。它不规定章节编号和固定顺序。模块级、接口级或流程级文档只保留与其接口、数据、状态、错误和验证有关的内容模块。

```markdown
# <设计对象> Spec

> [!abstract] 文档目的
> 本文定义……，覆盖……，可作为……工作的共同依据。

| 项目 | 内容 |
| --- | --- |
| 文档状态 | 设计规格 |
| 适用对象 | …… |
| 适用范围 | …… |
| 相关资料 | [[相关 Spec]] |

---

## <术语、角色与约定>

- 规范用语、缩略语、命名和范围

## <目标、假设、限制与配置>

- 定型目标、参数、资源、前置条件和不支持项

## <架构、组件与职责>

- 总图、子图、职责表、主要对象和依赖关系

## <接口与数据契约>

- 端口、API、消息、配置、地址、格式、版本和错误返回

## <状态、流程与时序>

- 生命周期、请求处理、暂停、超时、停止、恢复和完成条件

## <功能、算法或操作定义>

- 操作表、字段、公式、数值行为、布局和限制

## <资源、安全、错误与恢复>

- 权限、容量、并发、故障、清理、回滚和审计要求

## <端到端场景与角色分工>

- 正常场景、错误场景、各角色动作和可观察结果

## <验证与定型约束>

- 验收场景、极限与异常用例、固定条件汇总
```

该模板是内容选择器，不是用空标题填充篇幅的清单。文档作者应以读者理解路径安排内容模块；每个保留模块都必须写入与当前设计一致、可由接口或验证检查的内容。
